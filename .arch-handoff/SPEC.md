## AD-7: Ресурсный инвариант GB10 — одна нагрузка за раз

- **Binds**: инференс, сбор траекторий, среда ↔ DGX Spark (128 ГБ unified)

- **Binds**: смета ↔ аренда GPU ↔ стоп-правило обучения
- **Prevents**: молчаливый перерасход на длинном претрейне или RL — сумма выясняется по факту, когда откат уже невозможен

Отсутствие сметы — блокирующее условие запуска. Смета — артефакт `evidence/budget/<run-ref>.json` (поля `run_ref`, `gpu_type`, `gpu_hours_estimate`, `usd_estimate`, `limit_usd`, `budget_method`, `stop_rule`, `created_at`, `approved_by`). Страж: C-041 (behavioural: смета существует до запуска, `usd_estimate ≤ limit_usd`, дата сметы раньше даты прогона); C-022 — документарная гигиена решения ADR-004, не страж инварианта.

## AD-9: Длинноконтекстные механизмы объявлены до претрейна и проверяются на гэпе

- **Binds**: `net/` (KDA, Gated MLA, SWA-ветка, indexer) ↔ NFR-005 (1M) ↔ критерии приёмки A4 ↔ `net/config.json.deviations`
- **Prevents**: расхождение исполнителей в способе лечить провал recall-in-context — один увеличивает долю Gated MLA, другой вводит sparse-выбор, третий тянет Engram-память. Это несовместимые реализации, каждая из которых стоит отдельного претрейна, тогда как проверка на скелете стоит ≈$200
- **Rule**: любое изменение механики длинного контекста (окно SWA, `top_k` выбора, шаринг проекций, FP4 латентного KV) вносится **декларативно** — параметром `net/config.json` и строкой в `deviations`, а не правкой кода по месту; плотный путь внимания сохраняется в коде как оракул за флагом до снятия гейта A4; замер — на 64K, вердикт механический (ADR-009, критерии 1–7). Заявления о достижении 1M на скелете запрещены: 1M остаётся критерием L1. Страж: C-034 (решение оформлено до реализации); C-035 (декларативность механики в `net/config.json`) активируется вместе с дельтой при ратификации — до реализации она даёт красный гейт и потому не внесена.
- **Pending evidence**: [PENDING-EVIDENCE: поведенческий страж декларативности — сверка полей `net/config.json` (swa_window, mla_top_k, шаринг KDA-проекций, FP4 латентного KV) с кодом `net/` и замер 64K по критериям 1–7 ADR-009; вместе с дельтой C-035 после реализации `net/`. Сегодня проверяется только наличие решения до реализации (C-034, structural)]

## AD-11: Вердикт не зависит от окружения — бэкенд, точность и детерминизм запиннены

- **Binds**: приёмочные прогоны сети ↔ бэкенд и политика точности матмулов ↔ режим детерминизма операций ↔ заголовок вердикта и манифест
- **Prevents**: один и тот же коммит даёт разные вердикты в разных оболочках. Зафиксировано: критерий 2 (порог 1e-4) на дефолтной политике — 3.37e-04 на GPU против 6e-08 на CPU (политика tf32-класса, не алгоритм); прогоны 18:07 и 19:15 одного дня — `test_10` PASSED/SKIPPED и `test_02` FAILED/PASSED из-за `LD_LIBRARY_PATH`; A5-детерминизм манифеста на GPU не держался (расхождение `workspace_sha256`), пока не включены детерминированные операции XLA.
- **Rule**: пиннинг — в `net/tests/conftest.py` как единственной точке: политика `highest`, бэкенд выбирается сьютом и объявляется, в гейтовом профиле — детерминированные операции XLA; заголовок прогона печатает политику, устройства и режим детерминизма, и вердикт без этой строки доказательством не считается; отсутствие GPU в гейтовом профиле — FAIL, SKIP только для локальных прогонов. Пороги критериев при этом не меняются. Страж: C-042 (runtime-конфигурация JAX, не текст файла).
- **Статус**: [ADOPTED] (13.09.2026 — критерий 2 под пиннингом 1.341e-07; A5: 3 из 3 прогонов на GPU без расхождения)
- **Source**: ADR-010, ADR-013

# ADR-011. Предметность стражей: fitness-правила проверяют поведение, а не прозу

- Date: 2026-09-13
- Status: Accepted (решение владельца 2026-09-13: принято, одновременно запущена первая дельта — AD-4)
- Route: Fast (significance_score = 0 по 15 триггерам) — но решение касается самого контрольного контура, поэтому оформлено ADR и вынесено на решение владельца добровольной эскалацией
- Порядок внесения: стражи контура (C-036, C-037) и переклассификация правил вводятся дельтами в изолированных ветках; основная ветка остаётся зелёной до мержа каждого стража — красный гейт живёт в ветке, а не в main

## Context

Спайн кейса объявляет 9 инвариантов (AD-1…AD-9), и все они формально «привязаны к fitness-правилам» (`verified_by` в `model/AD-*.md`, `trace_check` — AD → fitness 9/9, PASS). Проверка фактической силы этих стражей (13.09.2026, `fitness_check` по корневому `CONSTRAINTS.yaml` — 34 правила, 0 нарушений, PASS) показывает разрыв между объявленным и форсируемым:

**1. 82% правил не проверяют систему.** Распределение по `type`: 21 `must_contain` + 7 `each_file_must_contain` = 28 правил проверяют наличие текста в документах; 2 `must_not_contain` (заглушки C-007, секреты C-011); 1 `file_exists`; 3 `command_succeeds`, из которых предметных два — C-032 (нет копий весов в рабочем каталоге, только симлинки на `~/gb10-shared`) и C-033 (нет файлов >500 МБ), третий — C-034 (существует файл `docs/adr/ADR-009-*.md`).

**2. Самый подтверждённый инвариант защищён самым декоративным правилом.** AD-7 (`[ADOPTED]` — единственный, унаследован от ADR-013 платформы Spark и подтверждён инцидентами NVRM OOM 02.08/04.08) → C-012: `must_contain` по шаблону `AD-7|одна нагрузка за раз` в `ARCHITECTURE-SPINE.md`. Правило проверяет существование надписи; факт «на Spark исполняется одна нагрузка» не проверяется ничем.

**3. Правило о пиннинге само не запинено.** AD-4 («прогон без пиннинга не считается доказательством») → C-019: `must_contain` по шаблону `хеш|hash` в прозе `docs/adr/ADR-004-*.md`. При этом `evidence/README.md` требует `evidence/a4-skeleton-run-manifest.json` с хешами весов, датасета и версий среды — **файла в `evidence/` нет** (каталог содержит только `README.md` и `gate-snapshot-2026-09-12.md`). Невыполненный инвариант AD-4 не покраснел ни на одном гейте.

**3а. Аудит стражей инвариантов (13.09.2026, по полю `verified_by` в `model/AD-*.md`).** На 9 AD-инвариантов приходится 11 привязок: 10 правил `must_contain` и 1 `command_succeeds` — C-034, который проверяет лишь существование файла `docs/adr/ADR-009-*.md` и по существу тоже документарен. **Поведенческих стражей у инвариантов — 0 из 9.** Два предметных правила кейса (C-032, C-033 — веса и датасеты только симлинками) не привязаны ни к одному AD, то есть работающий механический контроль существует отдельно от спайна и о расхождении инвариантов ничего не сообщает.

**4. Расхождение, против которого писано решение, уже случилось — и поймано человеком.** `evidence/gate-snapshot-2026-09-12.md`: «один и тот же коммит даёт разный вердикт критерия 2 на CPU и GPU — 6e-08 против 3.37e-04». Это предмет ADR-010 (`Proposed`, AD-блока в спайне нет). Обнаружено вручную, ресёрч-доком `docs/research/attn-cost-and-matmul-precision-2026-09-12.md`, а не стражем: спайн молчал, потому что решение ещё не было принято. Механизм предотвращения включился после инцидента, а не до.

**5. Канал прогона гейта сломан.** `fitness_check` без явного указания пути читает `.arch-handoff/CONSTRAINTS.yaml` и падает:
```
fitness_check: mapping values are not allowed in this context at line 7 column 9
```
Причина — заготовка генератора пакетов: элемент списка начинается с `- name: readme-exists`, а поля идут с отступом `    type:` (строка 7) — YAML-парсер ошибку видит, гейт не исполняется. Прогон по корневому `CONSTRAINTS.yaml` — PASS 34/0. Та же заготовка уезжает в handoff-пакет внешнему исполнителю, где может быть принята за рабочие правила (зафиксировано в снимке гейтов как известное, но бездейственное).

**6. Гейты не запускаются по событию.** `[hooks] specs = []` (конфиг харнесса); CI репозитория `домашний репозиторий` (`.github/workflows/ci.yml`) прогоняет только Rust-контур — fmt/clippy/test/MSRV, ни одного архитектурного гейта; `state/fleet/` пуст при 4 планах флота в `.arch-fleet/`. Следствие: «предотвращение» полностью зависит от того, вспомнил ли человек прогнать проверку.

**7. Метрика покрытия обманывает сама себя.** `trace_check` даёт ADR → CMP 9/9, потому что ADR-010 в `model/` не заведён; покрытие достигнуто исключением сущности из модели (снимок гейтов это признаёт: «при ратификации ADR-010 звено ADR→CMP уйдёт из 9/9»). Дрейф, не поймавший ни одним гейтом: копия спайна в worktree `домашний репозиторий-tui` — 8 AD против 9; `evidence/README.md` заявлял «31 правило» при фактических 34 (обе находки получены вручную). Звена AD ↔ ADR нет ни в спайне, ни в модели: явные ссылки на кейсовые ADR — 2 из 10.

**Сила, действующая против изменения:** текстовые правила дёшевы, детерминированы, не флейкуют и не требуют доступа к GPU; поведенческие — дороже, часть инвариантов машинно невыразима (ось победы, приватность корпуса).

## Decision

Ввести в кейсе обязательную классификацию стражей и запретить декоративный контроль для инвариантов:

1. **Обязательные поля правила.** Каждое правило в `CONSTRAINTS.yaml` с `severity: high|critical` несёт `kind: behavioural | structural | documentary` и `evidence:` — путь/команду/поле артефакта, по которому проверяется выполнение. Правило без `kind`/`evidence` — ошибка конфигурации, не правило.
2. **Запрет декоративного стража инварианта.** Правило, привязанное к AD-инварианту (через `verified_by` в `model/AD-*.md`), не может быть `kind: documentary`. `documentary` остаётся допустимым только для гигиены решений (наличие обязательных секций ADR — C-001…C-003) и никогда не считается доказательством инварианта.
3. **Инвариант без поведенческого стража — красный.** Каждый AD-инвариант обязан иметь ≥1 правило `kind: behavioural` (`command_succeeds`, `dependency_direction`, `context_boundary`, проверка поля артефакта). Инвариант, у которого машинно-проверяемой формы нет, помечается в спайне `[PENDING-EVIDENCE: <что и когда появится>]` — честная декларация вместо имитации контроля.
4. **Мета-валидатор конфигурации.** Вводится C-036: `command_succeeds` запускает `tools/check_constraints_meta.py`, проверяющий пункты 1–3 и печатающий таблицу «инвариант → behavioural-страж → evidence». Валидатор — исполняемый код: пишется кодовым харнессом по handoff-пакету, архитектор его не пишет.
5. **Починка канала гейта — C-037.** Handoff-пакет содержит рабочий `CONSTRAINTS.yaml` кейса (не заготовку): правило проверяет совпадение набора правил в `кейс/CONSTRAINTS.yaml` и `кейс/.arch-handoff/CONSTRAINTS.yaml` (по числу правил и хешу). Заготовка с невалидным YAML в пакет не попадает.
6. **Запуск по событию.** Гейт исполняется не по памяти: fleet-гейт перед мержем (`merge_gate = owner` уже включён) + hook на правки в каталоге кейса. До включения поведенческих правил hook не активен, чтобы не подвешивать работу на неполном наборе.

Первый принудительный перевод (переклассификация 28 правил и написание поведенческих стражей для AD-2, AD-4, AD-7, AD-8) — отдельные дельты, по одной на инвариант, с прогоном C-036 на каждой.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Статус-кво**: оставить `must_contain` как форму стража | Дёшево, детерминированно, не флейкует, не требует доступа к GPU; ничего не ломается сегодня | Гейт PASS при невыполненном AD-4 и непринятом ADR-010; самый подтверждённый инвариант (AD-7) защищён надписью; расхождения ловит человек (счёт 2:0 не в пользу спайна); регрессия стоимости прогона обнаружится на A5, когда откат дорог |
| **Полный отказ от текстовых правил**: оставить только `command_succeeds` / `dependency_direction` | Чистая предметность, гейт падает только по факту | Машинно невыразимы AD-1 (ось победы), AD-6 (приватность корпуса), AD-5 (верность техотчёту) → 21 правило пришлось бы удалить; гейт из 6 правил даёт ложное чувство покрытия; часть контроля исчезает без замены |
| **Отказ от спайна в пользу дельта-спек** (инварианты живут в каждой дельте) | Меньше артефактов, каждая дельта самодостаточна, ближе к потоку работы | Инвариант перестаёт быть общим: две дельты, решающие локально, разойдутся несовместимо (AD-9: доля Gated MLA против sparse-выбора против Engram — по отдельному претрейну каждая); совместимость дельт не проверяется ничем, потому что проверять нечем; `trace_check` не имеет точки сверки |
| **Выбранный**: классификация `kind`/`evidence` + запрет documentary на инвариантах + обязательный behavioural-страж + мета-валидатор C-036 + починка канала C-037 + запуск по событию | Гейт краснеет на невыполненном инварианте, а не на отсутствии слов; появляется осмысленная метрика «сколько правил упало за период»; `[PENDING-EVIDENCE]` заменяет имитацию честной декларацией | Разовая работа: переклассификация 28 правил, написание поведенческих стражей, сопровождение валидатора; поведенческие правила дороже и могут флейковать (пример — вырожденный порог test_06, пойманный в `2cea836`) |

## Consequences

### Positive

- Гейт кейса начинает отражать состояние системы, а не состояние документации: невыполненные AD-4 (нет `a4-skeleton-run-manifest.json`), AD-7 (нет проверки занятости GB10), AD-10 (нет пиннинга бэкенда/точности) краснеют механически.
- Появляется метрика контроля, пригодная для отчётности владельцу: число упавших правил за период и доля расхождений, пойманных автоматически против вручную (сегодня 0 против 2).
- `[PENDING-EVIDENCE]` в спайне отделяет честно объявленное от проверяемого: инвариант без машинной формы перестаёт выглядеть защищённым.
- Мета-валидатор C-036 делает невозможной тихую деградацию самого контура контроля: добавить декоративное правило на критичный инвариант больше нельзя.
- Починка канала (C-037) устраняет класс ошибок «исполнитель получил пакет с нерабочими правилами и не узнал об этом».

### Negative

- Разовая стоимость: переклассификация 28 правил, написание поведенческих стражей минимум для AD-2, AD-4, AD-7, AD-8, затем — сопровождение валидатора. Оценивается в 4 отдельные дельты, не в одну правку.
- Поведенческие правила дороже и хрупче текстовых: требуют запуска команд, таймаутов, доступа к артефактам (GB10 для AD-7, реестр весов для AD-4). Возможны ложные красные при недоступности стенда — принимается явный режим `pending-evidence`, а не «зелёный по умолчанию».
- Часть инвариантов остаётся невыразимой машинно (AD-1 ось победы, AD-6 приватность корпуса). Их контроль остаётся процедурным; запрет documentary не превратит их в автоматический — только пометит честно.
- Валидатор C-036 сам является кодом и точкой отказа: ошибка в нём даст ложный PASS всему контуру. Митигация — валидатор покрыт собственными тестами и запускается на эталонной фикстуре с заведомо декоративным правилом (ожидаемый FAIL).
- Риск профанации в обратную сторону: перевод правил в `command_succeeds` с тривиальной командой (`test -n "$(ls ...)"`) даёт формально «поведенческий» страж без силы. Отсюда требование пункта 3 — `evidence` указывается и проверяется человеком на ревью дельты, а не только машиной.
- Переклассификация может вскрыть, что часть сегодняшних «critical» правил — гигиена документации; их понижение до `documentary` формально снижает заявленное покрытие ADR → CMP (9/9 перестанет быть 100%). Это ожидаемое следствие: метрика станет меньше, но правдивее.

## Reversibility

**costly.** Метаданные (`kind`, `evidence`, пометки `[PENDING-EVIDENCE]`) обратимы дёшево — это правка YAML и спайна без последствий для кода. Дорогая часть — поведенческие правила, уже участвовавшие в приёмке: после того как `a4-skeleton-run-manifest.json`, проверка занятости GB10 и пиннинг точности попали в вердикты гейтов A4/A5, их откат меняет сам вердикт и требует пересмотра evidence-пакета. Поэтому откат допустим только до прогона A4; после A4 решение де-факто фиксируется. Окно дешёвой смены — сейчас: модельный код не написан, A4 не закрыт (критерии 6 и 16 не выполнены по снимку 12.09.2026).

# ADR-014. Манифест прогона A4 несёт состав стадий конвейера; частичный прогон гейт не закрывает

- Date: 2026-09-13
- Status: Proposed
- Маршрут: **Standard** (`significance_score` = 3: new_component, data_contract_change, significant_nfr)
- Следствие: усиливает AD-4 (спайн) и behavioural-страж C-038; конкретизирует AD-10

## Context

**Рамка гейта.** A4 (conformance) определён как «скелет L3 воспроизводит конвейер и проходит среду и стенд»:
зелёный скелет — чекпойнт → инференс на Spark → RL-среда → SFT → RL по схеме базы (README, гейты).
Манифест прогона — механическое доказательство этого факта; AD-4 требует пиннинга весов, датасета, среды
и архитектурной базы, C-038 объявлен behavioural-стражем инварианта 13.09.2026
(`tools/a4_manifest.py --verify`, схема `a4-skeleton-run-manifest/v1`).

**Факт обследования 13.09.2026 (не гипотеза).** Прогонного пути A4 в коде кейса нет:

| Стадия конвейера A4 | Состояние в репозитории |
|---|---|
| pretrain_checkpoint | сеть (`net/model.py`), Orbax-чекпойнт с хешем (`net/checkpoint.py`) — есть; цикла обучения нет |
| spark_inference | `net/infer.py` есть; прогон на стенде gb10 — операторский, замер на RTX 4080 (`net/gpu-smoke-report.json`) |
| rl_environment | `env/` — среда, задачи, верификаторы, run manifest; `env/net_executor.py` + `net/tests/test_13_integration.py` — стыковка сети со средой |
| sft | **нет кода** |
| rl_base_scheme (схема базы, ADR-005 п. 2) | **нет кода** — существует лишь чужой GRPO-харнесс для Qwen2.5-0.5B (`benchmarks/spine-vs-claude/rl/grpo_manual.py`, коммиты `cb31759`/`53b879e`), не стадия нашего скелета |

**Отсюда дефект стража.** Схема v1 требует непустых полей `model_weights_sha256`, `dataset_sha256`,
`environment_version`, `harness_version`, `git_commit`, `run_date`, `run_ref` — и ничего не говорит о
покрытии конвейера. Прогон по **доступной сегодня** части (инициализация весов → чекпойнт → инференс →
RL-среда) пройдёт `--verify`, даст зелёный C-038 и **ложно закроет A4**, которого нет. Это ровно тот класс
дефекта, который AD-4 объявляет предотвращаемым («зелёный гейт при отсутствующем манифесте»), а AD-10
называет по имени: страж проверяет артефакт, а не предмет инварианта — «инвариант объявлен, гейт проверил
наличие надписи».

**Ограничения.** Фабрикация доказательства запрещена (AD-4, AD-10): манифест без реального прогона
недействителен. Стенд gb10 (Spark) не управляется из сборочного окружения — его стадия остаётся
операторской. Стадии SFT/RL по схеме базы — отдельная работа (ADR-005), её нельзя «сделать по дороге».

## Decision

1. **Схема манифеста прогона A4 поднимается до `a4-skeleton-run-manifest/v2`** и получает
   обязательные поля покрытия: `stage_set_version` (эталонный набор стадий), `stages` — список
   `{name, status: executed|skipped|absent, evidence}`, `pipeline_complete` (bool).
2. **Эталонный набор стадий `stage_set v1`** (соответствует A4 и ADR-005):
   `pretrain_checkpoint`, `spark_inference`, `rl_environment`, `sft`, `rl_base_scheme`.
   Расширение набора (например, MOPD-консолидация, ADR-005 п. 7) — только новой версией `stage_set`
   со ссылкой на решение; молча дорисовывать стадии запрещено.
3. **Полнота вычисляется, а не декларируется.** `pipeline_complete = true` тогда и только тогда,
   когда все стадии эталонного набора имеют `status: executed` и непустой `evidence`. Генератор
   вычисляет поле сам; переданное извне значение игнорируется.
4. **C-038 усиливается на месте** (не новым правилом): `--verify` возвращает ненулевой код, если
   схема не v2, состав стадий не покрыт эталонный набор или `pipeline_complete=false`; сообщение
   перечисляет **поимённо** непокрытые стадии и различает случаи «манифеста нет» / «покрытие частично: …».
5. **Красный по C-038 при частичном покрытии — штатное состояние, а не регресс.** Промежуточный прогон
   разрешён: он доказывает пиннинг и провод, пишет манифест с `pipeline_complete=false`, и гейт A4
   остаётся красным до появления стадий `sft` и `rl_base_scheme` и операторского `spark_inference`.
6. **Запрет фабрикации сохраняется без ослаблений:** генератор без `--weights-hash`/`--dataset-hash`/`--run-ref`
   завершается ненулевым кодом и ничего не пишет.
7. **Совместимость:** манифест v1 после этой дельты невалиден. Манифестов A4 в `evidence/` сегодня нет
   (каталог содержит только README и снимок гейтов), поэтому цена несовместимости сейчас нулевая.
8. **Портируемость путей (уточнение 13.09.2026, после приёмки дельты).** Все пути в манифесте
   (`run_ref`, пути внутри `stages[].evidence`) — относительные от корня репозитория; абсолютные пути
   запрещены, генератор нормализует абсолютный путь внутри репозитория и отклоняет путь вне него,
   `--verify` отклоняет манифест с любым абсолютным путём (K11–K12). Основание — дефект, найденный
   на приёмке: первый wire-прогон записал в `run_ref` и `evidence` абсолютные пути worktree флота,
   удалённого после мержа, из-за чего манифест стал непортируемым, A5-прогон по нему невозможен,
   а в артефакте оказались личные пути сборочной машины (гейт CI «personal paths»).

Артефакты решения: дельта-спека `docs/specs/A4-RUN.delta.md` (механическое определение прогона A4,
схема v2, критерии приёмки), правка `tools/a4_manifest.py`, правка Rule в спайне AD-4 и `model/AD-4`.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Статус-кво: оставить v1, сгенерировать манифест из доступного прогона** | минимум работы, C-038 зеленеет, «нарушений 0» достигнуто | ложно-зелёный гейт: A4 не пройден, а гейт говорит «пройден»; воспроизводится дефект, ради предотвращения которого AD-4 вводился; заявления о конвейере перестают быть проверяемыми. **Отвергнуто** |
| **Новое правило C-039 вместо усиления C-038** | существующий страж не трогаем | два стража одного инварианта с разными порогами = расхождение исполнителей в том, что считать доказательством (AD-10 Prevents); C-038 уже объявлен behavioural-стражем AD-4, усиление в нём сохраняет одну точку истины. **Отвергнуто** |
| **Не менять схему, а потребовать полноту прогона прозой в TASK/спеке** | нет правки контракта артефакта | непроверяемо механически: «прогон был полным» остаётся надписью; именно это AD-10 запрещает. **Отвергнуто** |
| **Требовать полный прогон немедленно, без промежуточного режима** | гейт строго честен с первого дня | блокирует всякое продвижение и доказательство пиннинга до готовности всех стадий; любая работа по частям объявляется нарушением, что толкает к обходу гейта. **Отвергнуто** (выбран промежуточный режим с честным `pipeline_complete=false`) |

## Consequences

### Positive

- Гейт A4 становится измеримым по покрытию, а не по наличию файла: видно, что именно уже доказано,
  а что нет — поимённо.
- Частичный прогресс разрешён и фиксируется, поэтому пиннинг снапшотов и провод «сеть ↔ среда»
  доказываются уже сейчас, не дожидаясь SFT/RL.
- Один страж на инвариант (C-038) — расхождение «что считать доказательством» между исполнителями
  структурно невозможно.

### Negative

- **Гейт по C-038 останется красным на весь период отсутствия стадий `sft` и `rl_base_scheme` и
  операторского `spark_inference`.** Метрика «нарушений 0» недостижима без реальной реализации
  конвейера — это сознательная цена честности. Митигация: сообщение стража различает «манифеста нет»
  и «покрытие частично: …», поэтому красный читается как план работ, а не как поломка.
- **Обратная несовместимость схемы v1** : любой существующий манифест v1 перестаёт проходить `--verify`.
  Сегодня манифестов нет, поэтому цена нулевая; после первого прогона она стала бы costly.
- **`stage_set` — тоже решение**: неполный набор стадий даст ложную полноту. Митигация — версия набора
  и обязательная ссылка на ADR-005 при расширении.
- **Стадия Spark остаётся операторской** и не может быть автоматически доказана из сборочного окружения;
  соблазн выставить `status: executed` по факту прогона на другой GPU (RTX 4080) отвергается правилом:
  `skipped` с причиной, а не подмена стенда.

## Reversibility

**Reversible.** Схема манифеста — контракт артефакта evidence, а не данных обучения: откат — вернуть
v1 в `tools/a4_manifest.py` (одна дельта кода), манифестов v2 к тому моменту либо нет, либо они
перегенерируются из того же прогона. Необратимость появится только после первого реального манифеста,
на который уже сослались внешние артефакты; до него откат бесплатен и не требует повторного прогона.

## Бэкенд и политика точности (ADR-010)

Вердикт сьюта не должен зависеть от оболочки, поэтому оба параметра пиннуются
в `net/tests/conftest.py` — в одном месте, а не в команде запуска:

* **политика точности** — `jax_default_matmul_precision="highest"`. Критерий 2
  (паритет форм KDA) на GPU при политике по умолчанию даёт 3.37e-04 против
  порога 1e-4; под `highest` — 1.2e-07 на CPU и GPU. Оракул обязан мерить
  алгоритм, а не политику точности железа; порог 1e-4 не меняется;
* **бэкенд** — выбирается явно: `nvidia-*` библиотеки венва предзагружаются
  до `import jax`, потому что с системной CUDA в `LD_LIBRARY_PATH` плагин
  подхватывает libcusparse, несовместимый по nvJitLink 12.9, и молча падает на
  CPU. Экспорт `LD_LIBRARY_PATH` вручную больше не нужен (и не должен
  переопределять venv).

Заголовок прогона печатает политику, `jax.devices()`, профиль
(`NET_GATE_PROFILE`) и режим детерминизма (ADR-013). Профили различают
требование GPU:

| Профиль | Как включить | Нет CUDA-устройства |
|---|---|---|
| gate (A4) | `NET_GATE_PROFILE=1` или `pytest --net-gate` | `test_10_gpu_smoke` — **FAIL** с внятным сообщением |
| local (предварительный) | по умолчанию | `test_10_gpu_smoke` — **SKIP** с явной причиной |

Переменные выбора: `NET_JAX_BACKEND=auto` (по умолчанию) \| `gpu` \| `cpu` —
`cpu` ставит `JAX_PLATFORMS=cpu`, чтобы явный выбор не переопределялся
окружением.

```bash
export LD_LIBRARY_PATH=$(ls -d ~/venv-axiom/lib/python3.11/site-packages/nvidia/*/lib | tr '\n' ':')
python -m pytest net/tests/test_10_gpu_smoke.py -q -s   # замер ток/с на GPU
python -m net.gpu_smoke                                  # отчёт net/gpu-smoke-report.json
python -m pytest net/tests/ -q                      # local: без GPU — SKIP, не PASS
NET_JAX_BACKEND=cpu python -m pytest net/tests/ -q   # предварительный прогон на CPU
NET_GATE_PROFILE=1 python -m pytest net/tests/ -q    # гейтовый профиль A4: GPU обязателен
python3 tools/check_precision_pinning.py --profile gate   # страж пиннинга (C-042)
python -m net.gpu_smoke                              # отчёт net/gpu-smoke-report.json
```

**Детерминизм (ADR-013).** В гейтовом профиле `conftest` добавляет
`--xla_gpu_deterministic_ops` в `XLA_FLAGS` — до `import jax`, потому что XLA
разбирает переменную один раз, при создании клиента. Без флага XLA не
гарантирует побитовое совпадение GPU-ядер, и A5 («повторный прогон → тот же
манифест», `workspace_sha256` считается по содержимому артефактов) держится
случайно. В локальном профиле флаг не ставится: скорость итераций важнее, а
заголовок честно печатает режим, в котором получен результат.

Страж `tools/check_precision_pinning.py` (правило C-042) проверяет не текст
conftest, а runtime-конфигурацию: применяет пиннинг в отдельном процессе и
читает обратно `jax_default_matmul_precision`, `jax.devices()` и наличие
`--xla_gpu_deterministic_ops` в `XLA_FLAGS` процесса (в гейтовом профиле его
отсутствие — FAIL). Режим `--measure-criterion2` подтверждает, что под
пиннингом критерий 2 укладывается в порог (без CUDA-устройства — SKIP с явной
причиной, не PASS).
