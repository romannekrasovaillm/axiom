# Задача для кодового харнесса

Добавить в per-step метрики pretrain-прогона диагностику градиента — без изменения поведения обучения.

ЗАЧЕМ: на шаге ~14391 длинного прогона loss устойчиво вырос (медиана 100: 4.54 → 4.78), данные и конфиг исключены. В метриках нет grad_norm, поэтому нельзя отличить численный сдвиг оптимизатора от локальной особенности данных. Нужна наблюдаемость.

ЧТО СДЕЛАТЬ:
1. В цикле обучения (net/train_loop.py, место вычисления градиентов до применения оптимизатора) вычислить глобальную L2-норму градиента по всему PyTree: sqrt(sum(x^2) по всем листьям). Учесть, что массивы могут быть шардированы: норма должна быть глобальной, не средней по устройствам.
2. Если в цикле есть клиппинг (проверить фактически; не выдумывать), вычислить:
   - grad_norm_preclip — норма до клиппинга;
   - grad_norm_postclip — норма после клиппинга (если клиппинга нет — равно preclip);
   - grad_clip_coeff — clip_norm / max(grad_norm_preclip, eps), 1.0 если клиппинга нет.
3. Записать эти поля в JSONL метрик рядом с step/loss/step_seconds. Схема pretrain-metrics/v1 расширяется обратносовместимо: существующие поля и их типы не меняются, новые ключи добавляются.
4. Значения — конечные float; если норма не конечна, писать фактическое значение (это диагностический сигнал), не подменять нулём.
5. Стоимость: не добавлять лишних device-синхронизаций на каждом шаге сверх необходимого; вычисление нормы не должно заметно менять время шага.

ТЕСТЫ (обязательны):
- unit: норма pytree (один лист, несколько листьев, нулевой градиент);
- unit: отсутствие клиппинга → postclip == preclip, coeff == 1.0;
- интеграционный на моке шага: поля присутствуют в записанной строке метрик;
- обратная совместимость: старый парсер метрик не падает на новых ключах.

ДОКУМЕНТАЦИЯ: коротко в docs — что означают три поля и как их читать (одна страница/секция, без переписывания существующих доков).

ГРАНИЦЫ:
- НЕ менять порядок операций, оптимизатор, клиппинг, RNG, данные, гиперпараметры.
- НЕ запускать длинные GPU-прогоны; тесты — CPU/моки.
- НЕ менять формат существующих полей метрик и не ломать потребителей.
- НЕ трогать код вне net/ и tools/ (кроме docs и тестов).

## Границы (scope)

Машинный контракт границ — `MANIFEST.json.scope` (хэш `scope_hash`); изменение вне границ ловится гейтом, а не обсуждается постфактум.

- **Можно писать:** `net/`, `tools/`, `docs/`
- **Нельзя писать (сильнее allow):** `model/`, `ARCHITECTURE-SPINE.md`, `CONSTRAINTS.yaml`
- **Можно запускать:** не объявлено — только чтение и правки в границах
- **Сеть:** сети нет (детерминированный узел)

## Финализация (обязательно)

Результат забирается из git, поэтому перед финальным ответом зафиксируй работу коммитом:

```bash
git add -A -- . ':!.arch-handoff'
git commit -m "<кратко: что реализовано>"
git status --short   # пусто, кроме .arch-handoff/
```

- Коммитится код и тесты; служебный каталог `.arch-handoff/` в коммит не входит.
- Работа без коммита считается невыполненной: оркестратор увидит её только через git log.

### Самопроверка через MCP (маршрут Standard/Critical — обязательна)

Перед финальным коммитом вызови через MCP-сервер `arch-spine` (подключён per-run, `.arch-handoff/mcp.json`) ровно эти проверки и добейся `passed=true`:

- `fitness_check` — `{"repo": "<корень прогона>"}`;
- `scope_check` — `{"repo": "<корень прогона>"}`.

Их вызовы пишутся в MCP-журнал прогона (`.arch-handoff/mcp-journal.jsonl`) — это evidence «исполнитель проверял себя». Отсутствие записей = непроверенное, а не проверенное: на приёмке такой прогон не засчитывается (INCOMPLETE). `handoff_status` показывает обязательные проверки маршрута, `contract_validate` — пройдёт ли контракт результата.

## Контракт результата

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа); тот же JSON запиши файлом `.arch-handoff/result.json` (файл переживает обрыв вывода):

Схема объекта: `{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}`

- `status`: `complete` — выполнено полностью; `partial` — частично; `blocked` — заблокировано.
- `assumptions`: допущения, принятые при реализации.
- `open_questions`: вопросы к архитектору.
- `conflicts_with_prior_decisions`: расхождения с принятыми ранее решениями (ADR, spine).

Архитектурный контекст — `ARCHITECTURE.md`, ограничения — `CONSTRAINTS.yaml`, рубрика приёмки — `RUBRIC.yaml` (при наличии).
