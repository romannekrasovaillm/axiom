# Задача для кодового харнесса

ЗАДАЧА (линия MFU-55, рычаг 2 после G1: устранить мелкоядерность TRSM в KDA).

КОНТЕКСТ (измерено на GB10, `evidence/mfu-55/G1/REPORT.md`). Предыдущий рычаг заменил `jnp.linalg.inv(eye + l_mat)` на батчевое `jax.lax.linalg.triangular_solve` (функция `_ut_solve` в `net/kda.py`, обе формы — `wyut` и `chunked_cc`). LU-факторизация ушла (`getrf_panel`/`LuPivotsToPermutation` исчезли), но **мелкоядерность не ушла**: профиль стационарной фазы показывает **115 200 ядер `batch_trsm_left_kernel<…,64,4,…>`** за 120 с (то есть `nrhs` дробится до 4) плюс **230 400 служебных `MakeBatchPointers`**, занятость GPU 3.5%, ток/с 380 против 406.7 у LU-версии. XLA батчевый TRSM в одно крупное ядро НЕ собирает.

ЧТО СДЕЛАТЬ (один рычаг).
1. **Слить две правые части в один вызов**: у `w` и `u` общая матрица `(I+L)` и разные правые части (`xw` и `vw`, каждая `(H, C, d)`) — склеить их по последней оси (`jnp.concatenate([xw, vw], axis=-1)`) и решить **одним** `_ut_solve`, затем разрезать результат. Ожидание: вдвое меньше вызовов TRSM при том же объёме — и, главное, крупнее `nrhs`.
2. Если после (1) в коде видно, что правая часть всё ещё подаётся срезами — рассмотреть вариант с батчеванием по головам в одну правую часть формы `(C, H*d)` (или `(H*C, d)`) так, чтобы TRSM получал крупный `nrhs`; выбор обосновать в отчёте.
3. Сохранить математику: результат в пределах существующих допусков тестов паритета (`net/tests/test_kda_chunked_cc.py`, `test_kda_wyut.py`) и стража `net/tests/test_kda_dtype_gate_parity.py` (он уже разделяет критерии по формам — не ослаблять его).
4. Добавить/дополнить тест, фиксирующий, что оба произведения (`w` и `u`) считаются одним вызовом решения (например, через monkeypatch-счётчик вызовов `_ut_solve` — ровно один на чанк-шаг вместо двух) и что разрез результата даёт прежние значения.

ОГРАНИЧЕНИЯ. Зона: `net/kda.py` + `net/tests/*`. GPU-прогоны НЕ запускать (замеры делает архитектор на GB10). Не трогать `net/config.json`, публичные сигнатуры, математику KDA, страж ADR-040 по существу. Один рычаг — один коммит.

ПРОВЕРКА (CPU, обязательно с этим интерпретатором — системный python без зависимостей): `/home/roman/venv-axiom/bin/python -m pytest -q net/tests/test_kda_chunked_cc.py net/tests/test_kda_wyut.py net/tests/test_kda_dtype_gate_parity.py`.

РЕЗУЛЬТАТ. `.arch-handoff/result.json` + ФИНАЛЬНЫЙ git-commit от исполнителя. В assumptions — на какой форме остановился (concat по последней оси vs батч по головам) и почему; в open_questions — что должен измерить архитектор на GB10 (ожидаемое падение числа TRSM-ядер с 115 200 и рост занятости).

## Финализация (обязательно)

Результат забирается из git, поэтому перед финальным ответом зафиксируй работу коммитом:

```bash
git add -A -- . ':!.arch-handoff'
git commit -m "<кратко: что реализовано>"
git status --short   # пусто, кроме .arch-handoff/
```

- Коммитится код и тесты; служебный каталог `.arch-handoff/` в коммит не входит.
- Работа без коммита считается невыполненной: оркестратор увидит её только через git log.

### Самопроверка через MCP (маршрут Standard/Critical — обязательна)

Перед финальным коммитом вызови через MCP-сервер `arch-spine` (подключён per-run, `.arch-handoff/mcp.json`) ровно эти проверки и добейся `passed=true`:

- `fitness_check` — `{"repo": "<корень прогона>"}`;
- `scope_check` — `{"repo": "<корень прогона>"}`.

Их вызовы пишутся в MCP-журнал прогона (`.arch-handoff/mcp-journal.jsonl`) — это evidence «исполнитель проверял себя». Отсутствие записей = непроверенное, а не проверенное: на приёмке такой прогон не засчитывается (INCOMPLETE). `handoff_status` показывает обязательные проверки маршрута, `contract_validate` — пройдёт ли контракт результата.

## Контракт результата

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа); тот же JSON запиши файлом `.arch-handoff/result.json` (файл переживает обрыв вывода):

Схема объекта: `{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}`

- `status`: `complete` — выполнено полностью; `partial` — частично; `blocked` — заблокировано.
- `assumptions`: допущения, принятые при реализации.
- `open_questions`: вопросы к архитектору.
- `conflicts_with_prior_decisions`: расхождения с принятыми ранее решениями (ADR, spine).

Архитектурный контекст — `ARCHITECTURE.md`, ограничения — `CONSTRAINTS.yaml`, рубрика приёмки — `RUBRIC.yaml` (при наличии).
