# Задача для кодового харнесса

ЗАДАЧА (Pallas-кернел KDA: точность fp32 — GPU-проверка показала tf32 вместо ieee).

ФАКТ (проверено архитектором на GB10, `check_kernel.py net/kernels/kda_ut_solve.py --seeds 3`, коммит `8f99ae4`):
- **case1 bfloat16 — PASS** (все сиды, bad=0.00%, max_abs≈0.031).
- **case0 float32 — FAIL** (все сиды): `max_abs≈0.0036–0.0040`, `bad≈61%`. Пример: out `-2.443359375` против ref `-2.442455768585205`.
Разница ~4e-4 относительно и «ступенчатый» характер значений (мантисса ~10 бит) — это **точность tf32**, а не fp32: входа fp32, но умножение/аккумулятор внутри кернела идёт через tf32 (Triton по умолчанию на fp32 использует tf32-путь). Для KDA это неприемлемо: решение `(I+L)X=B` в fp32 должно совпадать с `jnp.linalg.solve` в пределах fp32-допуска.

ЧТО СДЕЛАТЬ.
1. Задать явную точность вычислений в кернеле для fp32-режима: `input_precision="ieee"` (или эквивалент для используемого API: `tl.dot(..., input_precision=...)` / `pl.dot`), чтобы fp32-путь считался в полной точности. Для bf16-режима оставить как есть (он уже PASS).
2. Проверить, что fp32-ветка действительно не использует tf32 ни на одном из умножений/свёрток внутри тела кернела (перечислить в отчёте все точки `dot`/свёрток и их `input_precision`).
3. Учесть цену: `ieee` на тензорных ядрах может быть медленнее — это ожидаемо и измеряется на GB10 архитектором (architectural trade-off). В отчёте зафиксировать, что выбор `ieee` — сознательный (точность важнее), и что альтернатива (`tf32` + допуск) требует решения архитектора, а не молчаливого ослабления теста.
4. CPU-тесты: `net/tests/test_kernel_kda_ut_solve.py` остаются зелёными; если тесты сверяются с эталоном на CPU, должно сохраниться совпадение в пределах прежнего atol (1e-4).

ОГРАНИЧЕНИЯ. Зона: `net/kernels/*`, `net/tests/*`. GPU-прогоны не запускать (их делает архитектор). Не менять `net/kda.py`, `net/config.json`, контракт модуля, `block_shape`/`grid` (они уже исправлены и прошли GPU).

ПРОВЕРКА (ПК): `/home/roman/venv-axiom/bin/python -m pytest -q net/tests/test_kernel_kda_ut_solve.py`.

РЕЗУЛЬТАТ. `.arch-handoff/result.json` + ФИНАЛЬНЫЙ git-commit. В assumptions — какие точки умножения переведены на `ieee` и почему; в open_questions — ожидаемая потеря/цена производительности, которую архитектор измерит на GB10.

## Финализация (обязательно)

Результат забирается из git, поэтому перед финальным ответом зафиксируй работу коммитом:

```bash
git add -A -- . ':!.arch-handoff'
git commit -m "<кратко: что реализовано>"
git status --short   # пусто, кроме .arch-handoff/
```

- Коммитится код и тесты; служебный каталог `.arch-handoff/` в коммит не входит.
- Работа без коммита считается невыполненной: оркестратор увидит её только через git log.

### Самопроверка через MCP (маршрут Standard/Critical — обязательна)

Перед финальным коммитом вызови через MCP-сервер `arch-spine` (подключён per-run, `.arch-handoff/mcp.json`) ровно эти проверки и добейся `passed=true`:

- `fitness_check` — `{"repo": "<корень прогона>"}`;
- `scope_check` — `{"repo": "<корень прогона>"}`.

Их вызовы пишутся в MCP-журнал прогона (`.arch-handoff/mcp-journal.jsonl`) — это evidence «исполнитель проверял себя». Отсутствие записей = непроверенное, а не проверенное: на приёмке такой прогон не засчитывается (INCOMPLETE). `handoff_status` показывает обязательные проверки маршрута, `contract_validate` — пройдёт ли контракт результата.

## Контракт результата

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа); тот же JSON запиши файлом `.arch-handoff/result.json` (файл переживает обрыв вывода):

Схема объекта: `{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}`

- `status`: `complete` — выполнено полностью; `partial` — частично; `blocked` — заблокировано.
- `assumptions`: допущения, принятые при реализации.
- `open_questions`: вопросы к архитектору.
- `conflicts_with_prior_decisions`: расхождения с принятыми ранее решениями (ADR, spine).

Архитектурный контекст — `ARCHITECTURE.md`, ограничения — `CONSTRAINTS.yaml`, рубрика приёмки — `RUBRIC.yaml` (при наличии).
