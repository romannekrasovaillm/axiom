# ADR-010. Бэкенд и политика точности матмулов пиннутся в приёмочных тестах сети: вердикт гейта не зависит от окружения

- Date: 2026-09-12
- Status: Accepted (решение владельца 2026-09-13: пиннинг бэкенда и политики точности в приёмочных тестах принят; альтернативы «мерить на дефолтном окружении» и «пиннить только бэкенд» отклонены)

## Context

Механический вердикт net-сьюта кейса axiom зависит от окружения запуска, а не только от кода:

1. **Бэкенд.** Пакеты `nvidia-*` в venv установлены, но плагин CUDA инициализируется только когда
   `LD_LIBRARY_PATH` указывает на их `lib/`. Без этого `jax.devices()` даёт `[CpuDevice(id=0)]`,
   с ним — `[CudaDevice(id=0)]`. Один и тот же коммит в один день дал два разных вердикта:
   прогон 18:07 — `test_10_gpu_smoke` PASSED и `test_02_kda_parity` FAILED; прогон 19:15 —
   `test_10` SKIPPED и `test_02` PASSED.
2. **Политика точности.** Критерий 2 (паритет рекуррентной и чанкованной форм KDA, порог 1e-4)
   на GPU при `jax_default_matmul_precision=None` (значение по умолчанию) даёт 3.37e-04, при
   `high`/`highest` — 1.2e-07. На CPU — 6e-08 при любом chunk. Расхождение при chunk=1 равно
   1.3e-06, при любом chunk≥2 сразу 3.3e-04 и не растёт ни с размером чанка, ни с длиной —
   то есть это не накопление суммы, а фиксированный вклад точности мантиссы (2⁻¹¹ ≈ 4.9e-04,
   tf32-класс). Матмулы есть только в чанкованной форме (`_delta_transitions`, `_combine`) —
   поэтому политика точности задевает ровно одну из двух форм, которые тест сравнивает.

Замеры и команды воспроизведения: `docs/research/attn-cost-and-matmul-precision-2026-09-12.md`.

Ограничение контура: AD-2 требует механического вердикта, AD-4 — пиннинга. Вердикт, который
переключается переменной окружения оболочки, механическим не является и доказательством A4 быть
не может: прогон на другой машине (или из другого терминала) даст другой результат при неизменном
коде. Целевая платформа скелета — GPU (ADR-008), поэтому «зелено на CPU, красно на GPU» — не
допустимая неопределённость: красный на GPU вердикт критерия 2 относится к той платформе, на
которой механизм будет обучаться.

## Decision

Приёмочные тесты сети (`net/tests/conftest.py`) пиннят оба параметра явно, в одном месте, и
объявляют платформу в вердикте:

1. `jax.config.update("jax_default_matmul_precision", "highest")` в conftest — оракулы проверяют
   **алгоритм**, а не политику точности железа. Порог критерия 2 (1e-4) остаётся неизменным.
2. Бэкенд выбирается **явно и объявляется**: тест печатает `jax.devices()` в заголовке прогона;
   запуск с GPU обязателен для гейта A4 (критерий 10 `test_10_gpu_smoke` — не SKIP, а PASS),
   прогон на CPU считается предварительным и помечается как таковой.
3. `test_10_gpu_smoke` перестаёт быть «проходящим по обстоятельствам»: отсутствие GPU даёт
   FAIL с внятным сообщением в гейтовом профиле, SKIP остаётся только для локальных прогонов
   без явного требования GPU.

Точность чанкованной формы при **тренировочных** политиках (tf32/bf16) — отдельный предмет: там
ожидаемое расхождение против рекуррентного эталона больше и порог 1e-4 к ней не применим. Это
выносится в отдельное решение при переходе к QAT/претрейну, а не измеряется оракулом паритета.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Оставить как есть, понизить порог критерия 2 до 5e-4 | Ноль работы; тест зелёный на обоих бэкендах | Маскирует механизм: порог перестаёт отличать дефект алгоритма от политики точности; вердикт по-прежнему зависит от окружения (на CPU расхождение 6e-08 — тест «проходит» с 8000-кратным запасом, ничего не проверяя) |
| Пиннить только бэкенд (GPU), политику оставить по умолчанию | Оракул гоняется на целевой платформе | Тогда красный `test_02` на GPU придётся объяснять в каждом прогоне; критерий 2 фактически становится критерием политики точности, а не паритета алгоритмов |
| Пиннить `jax_default_matmul_precision="high"` (не `highest`) | Ближе к тренировочной реальности; на GPU заметно быстрее | «high» — тоже разреженная точность; оракул перестаёт быть оракулом. Для проверки точности на тренировочной политике нужен отдельный тест с отдельным порогом |
| **Пиннить `highest` + объявлять бэкенд в вердикте (принято)** | Критерий 2 измеряет алгоритм; вердикт воспроизводим между машинами; расхождение при тренировочных политиках выносится в явный, отдельно сформулированный критерий | Прогон на GPU медленнее; требуется явное требование GPU в гейтовом профиле A4 |

## Consequences

### Positive

- Критерий 2 становится воспроизводимым: 1.2e-07 на CPU и GPU, вердикт не зависит от оболочки.
- Механизм расхождения зафиксирован в ADR, а не в переписке: следующий исполнитель не будет
  искать дефект в `kda.py` (SWA-ветка и чанкованный алгоритм проверены и исключены).
- Появляется место, куда явно ложится будущий критерий точности при тренировочных политиках.

### Negative

- Приёмочный прогон требует GPU: на машине без CUDA-плагина A4-прогон теперь невозможен без
  явного понижения до «предварительного». Это осознанная цена — иначе вердикт не механический.
- Прогон с пиннутым `highest` на GPU медленнее, чем с политикой по умолчанию (на 8K-замере цены
  разница ~4%: 10.27 против 9.90 мс).
- Тесты становятся зависимыми от версии JAX-конфига: переименование ключа `jax_default_matmul_precision`
  в будущих релизах сломает пиннинг молча, если не поставить страж (см. References).

## Reversibility

**reversible.** Обе настройки — одна строка в `net/tests/conftest.py`; откат возвращает прежнее
поведение (включая нынешнюю зависимость вердикта от окружения). Продуктовый код (`net/kda.py`,
`net/mla.py`) не меняется вовсе: решение касается только контура приёмки.
