# Инструкция для контрибьюторов (RU)

Добро пожаловать. Этот документ — карта входа в проект: что здесь происходит, как развернуть
окружение, где читать и что править, и по каким правилам принимается работа.

## 0. Что за проект — на одном примере

Мы учим модель-агента, которая сама работает с кодом. Не «чат про код»: агент получил задачу —
покопал в репозитории — внёс изменения — отчитался. Вердикт выдаёт не человек и не другая LLM,
а **механические правила** (fitness-гейты), зашитые в репозиторий.

Реальный случай, чтобы было понятно. 13 сентября мы построили манифест прогона — файл, где
пиннятся хеши весов, датасета и список стадий конвейера. Схема v1 проверяла: «хеши непустые?
зелёный». Звучит разумно. Но потом выяснилось: можно прогнать только четверть конвейера,
манифест будет с непустыми хешами — и гейт скажет «готово». Ложный зелёный хуже честного
красного: на нём строятся следующие шаги. Переписали схему так, чтобы `pipeline_complete`
считался машиной, а половинчатый прогон давал красный со списком недостающих стадий.

Вот ядро проекта: **агент учится на траекториях, где награда — пройденные механические проверки,
а не «похоже на правду»**. Сеть с нуля (KDA + MLA + LatentMoE на JAX), своя RL-среда и
конвейер данных существуют ради такого агента.

## 1. Окружение (10 минут)

```bash
git clone https://github.com/romannekrasovaillm/axiom.git
cd axiom

# тесты харнесса идут без JAX
python3 -m pytest tools/tests -q          # ~1 минута

# сетевые тесты — нужен JAX-venv
python3 -m venv venv-axiom
venv-axiom/bin/pip install -r env/requirements.txt
LD_LIBRARY_PATH=$(ls -d venv-axiom/lib/python3.11/site-packages/nvidia/*/lib | tr '\n' ':') \
  venv-axiom/bin/python -m pytest net/tests -q   # без GPU пойдёт на CPU, медленнее
```

Если есть GPU: экспортируй `LD_LIBRARY_PATH` (строка выше) — тесты пойдут на карту.
Без неё — CPU-режим, медленнее, но те же вердикты (пиннинг бэкенда гарантирует это).

## 3. Куда не лезть руками

Эти пути защищены дельта-протоколом (правки — только через ADR и решение владельца):
`ARCHITECTURE-SPINE.md`, `docs/adr/`, `docs/specs/`, `model/`, `CONSTRAINTS.yaml`,
`evidence/` (манифесты и следы прогонов). Если кажется, что правило неверное — это задача
на новый ADR (анти-ослабление, ADR-011), а не правка правила.

## 4. Правила, без которых не принимается работа

1. **ADR раньше кода.** Архитектурное решение — сначала документ, потом реализация.
2. **Анти-ослабление.** Fitness-правило, которое стало неверным, заменяется новым с обоснованием — гейт отслеживает ослабления.
3. **Fail-closed.** Проверка, которая не смогла выполниться, даёт FAIL, а не пропуск.
4. **Evidence раньше реализации.** Критерии приёмки и план отката пишутся до кода.
5. **Скраб первой ступенью** в любом пайплайне над логами; `SALT`/`sha256` — не секреты, `*_TOKEN` — секреты.

## 5. Как выглядит рабочая дельта

Реальный цикл из жизни проекта (дельта «манифест v2»):

1. задача формулируется с критериями приёмки и планом отката (что откатывать и по каким сигналам);
2. реализация в ограниченных путях (`tools/`, при необходимости минимально `net/`);
3. прогоны: тесты дельты + полный regression-сьют + стражи;
4. отчёт: что сделано, числа, что не сделано и почему, открытые вопросы;
5. коммит одним набором изменений; гейт прогоняется на итоговом дереве.

Полный сьют на GPU занимает ~1:10 (374 теста) — закладывай время, а не «быстро проверю».
CPU-сьют технически возможен, но растягивается в часы — не мучай ни себя, ни хост.
