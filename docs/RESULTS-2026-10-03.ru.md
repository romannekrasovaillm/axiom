# Отчёт 03.10.2026: стенд GB10 поднят и верифицирован; пилот l3-full упёрся в стену памяти графа

Сессия «запуск на локальном стенде вместо аренды». Итог двойной: стенд работает
end-to-end (шаги идут, метрики и чекпойнты пишутся), но пилот `l3-full` при
T=8192/vocab 160k объективно не влезает в 128 ГБ — кит сидит **внутри** слоя,
а не между слоями, и послойный grad-checkpointing его не режет.

## Блокер: l3-full @ T=8192, vocab 160k — граф просит ~890 ГиБ

Два воспроизведённых OOM на стенде (журналы `~/axiom-run/pilot.log`,
`pilot-perlayer-fix-20261003.log`):

| Прогон | Конфигурация remat | hlo_rematerialization | Итог |
|---|---|---|---|
| 09:05 | coarse `jax.checkpoint(loss_fn)` | 889,93→889,84 ГиБ | OOM 888,37 ГиБ |
| 13:27 | per_layer + coarse (вложенно) | 889,93→889,84 ГиБ (байт-в-байт) | OOM 888,26 ГиБ |
| 16:xx | per_layer без coarse (фикс `282c47f`) | 892,92→892,83 ГиБ | OOM 891,46 ГиБ |

Измерения по цепочке диагноза (все воспроизводимы):

1. **CPU-бэкенд не годится для памяти**: `memory_analysis` на CPU игнорирует
   remat — per_layer 1094,53 ГиБ против none 1095,19 ГиБ (дельта 0,06%).
   Опт-in тест `AXIOM_GRAD_CKPT_MEMORY=1`
   (`test_24::test_full_config_compile_memory_manifest`) на CPU падает:
   1094,5 ГиБ при цели ≤50 ГиБ — критерий TASK «компиляция не просит >50 ГиБ»
   объективно не выполнен.
2. **На GPU remat работает**: тривиальная цепочка из 6 матричных шагов на
   4080 — 3,00 ГиБ plain против 2,00 ГиБ remat (default и nothing_saveable
   одинаково). Механизм `jax.checkpoint` исправен, дело не в нём.
3. **Кит — внутри слоя**: stablehlo графа несёт ~311 тензоров
   `(12, 8192, 128, 128)` fp32 (6,44 ГиБ каждый — траектория состояний KDA
   O(T·dk·dv) на голову) и ~736 тензоров `(12, 8192, 8192)` fp32 (3,22 ГиБ —
   dense-reference T×T скоры). Послойный remat ограничивает живой набор
   **одним** слоем, но один слой при T=8192 уже несёт десятки ГиБ — и XLA при
   симуляции не получает выигрыша (см. строки hlo_rematerialization выше).

**Исправленный дефект (не причина стены, но реальный)**: `train_loop`
оборачивал весь loss в coarse `jax.checkpoint` поверх послойных remat внутри
`compute_loss` — вложенность, вредная по смыслу. Фикс `282c47f`: обёртка
применяется только при `grad_ckpt_policy=none`; журнал прогона теперь несёт
`loop.grad_ckpt_policy`. Тесты L-11 (шпион на `_checkpoint_policy`) — обе
стороны поведения.

**Уточнение по блокам (CPU-замер `memory_analysis`, T=8192):** 4 слоя — 235,08 ГиБ,
8 слоёв — 400,98 ГиБ → **41,5 ГиБ на слой + постоянная часть ≈69 ГиБ**
(экстраполяция на 24 слоя = 1065 ГиБ ≈ замеренные 1094/1095). Постоянная
часть — CE-путь по vocab 160k (логиты NTP+MTP и их градиенты, ~73 ГиБ тензоров
в stablehlo) плюс веса/оптимизатор. Следствие: даже идеально honoured
послойный remat дал бы пик ≈ 69 (пол) + 41,5 (пересчёт одного слоя) + ~10
(траектория/веса) ≈ **120 ГиБ — всё равно выше пула 76,8 ГиБ**. Ключевой
кирпич — **чанкованный cross-entropy**: срезание пола до ~10–15 ГиБ опускает
пик до ~67 ГиБ и l3-full@8192 помещается в пул 0,6×128 ГБ без перепаковки
данных.

**Что реально снимет стену (на решение архитектора)**:

1. **чанкованный cross-entropy по vocab 160k (ключевой)**: логиты
   `(1,8192,160000)` fp32 = 5,24 ГиБ × ~14 копий NTP/MTP/градов — пол ~69 ГиБ,
   который одной своей массой почти заполняет пул; чанкинг по T (как в
   cut-cross-entropy/FLA) срезает его до ~10–15 ГиБ;
2. чанкованный по T backward внутри KDA (пересчёт траектории состояний
   кусками, как в FLA-реализациях delta-rule), а не хранение O(T·dk·dv) на
   голову — 41,5 ГиБ на слой в пересчёте;
3. операционный обход для пилота механики: перепаковка tokens на T=2048
   (манифест packed-данных сейчас строго 8192 — честный отказ
   `seq_len манифеста W (8192) != заказанного 2048` сработал) — смета пилота
   уже предполагает «пул 4×2048»;
4. расследование флагов XLA (почему собственный remat-проход XLA отказывается
   переразмещать большие регионы — 889,93→889,84 это 0,01%).

## Операционное: earlyoom на стенде

На стенде живёт `earlyoom -r 3600` (SIGTERM при MemAvailable ≤10%): на UMA
пул XLA считается занятой памятью при касании, и прогон pretrain с
`XLA_PYTHON_CLIENT_MEM_FRACTION=0.4–0.6` был убит дважды (journalctl -u
earlyoom, 13:02). Рецепт прогонов на стенде: `MEM_FRACTION ≤ 0.25` для
малых/средних пресетов, один тяжёлый прогон за раз (AD-7), учитывать активную
llm-platform (llama-server стартует по запросам и отъедает память сверху).
Конфиг earlyoom не трогали — это системное решение владельца стенда.
