# Ранбук стенда GB10 (axiom)

Операционный ранбук: процедуры эксплуатации стенда. Канонические ограничения живут в `ARCHITECTURE-SPINE.md` (AD-6/AD-7/AD-8) и `CONSTRAINTS.yaml` (C-040/C-041 и др.) — здесь только процедуры и ссылки на них. Источник брони предмета замера — пакет уроков Лагуны `docs/research/LESSONS-LAGUNA-LADDER.ru.md` §1.3 (LAG-ADR-058), §5.1–5.2 (LAG-ADR-007/008/011/023).

## 1. Окно стенда: одна тяжёлая нагрузка

- **AD-7**: на GB10 — одна тяжёлая нагрузка. Регламент окна «пилот xor llm-platform» (утверждён 04.10): перед длинной ногой `docker stop llm-platform-runtime`, после завершения — возврат.
- Перед стартом ноги: `nvidia-smi --query-compute-apps` + `free -g`; чужая/неучтённая нагрузка — стоп и вопрос владельцу.
- Watcher возврата платформы — журналируемый фоновый процесс (`watcher.log`), не «безымянный nohup» (§5.2 уроков: детачи без журнала запрещены).

## 2. Пороги свободной памяти — по стадиям, формула «прирост + 15%»

- Порог стадии = прирост памяти стадии (замеренный на её smoke) + 15%. Меньше порога — стоп и ожидание окна, не «попробуем».
- Эталон endurance-ноги (l3-full@8192, B=1): после остановки llama-server доступно ~23 ГиБ; нога держит хост ~113/121 ГБ.
- earlyoom на стенде: SIGTERM при MemAvailable ≤10%. Рецепт JAX: `XLA_PYTHON_CLIENT_MEM_FRACTION ≤0.6` **только** с `XLA_PYTHON_CLIENT_PREALLOCATE=false`; малые/средние пресеты — ≤0.25.
- Сигнатура OOM-каскада (инцидент 26.09): несколько независимых процессов умерли в одну минуту, логи без traceback → проверять `journalctl -k | grep -i oom` (нужны права root).

## 3. Штатная остановка и resume

- Остановка — только стоп-файлом `touch ~/axiom-run/STOP` (не kill): нога доходит до чекпойнт-границы.
- `--resume` на пустом каталоге чекпойнтов — честный отказ, а не свежий старт; первую ногу запускать без `--resume`.
- Между окнами — resume-ноги; смета `evidence/budget/<run-ref>.json` составляется до старта (AD-8/C-041), превышение — остановка с журналом.
- Запуск detached: `setsid nohup … < /dev/null` (stdin обязателен `/dev/null`, иначе ssh висит), лог + журнал + pid в сводке.

## 4. Бронь предмета замера (обязательно до длинных проб)

Проблема: ретенция раннера `--keep-last` по умолчанию 2 (`tools/pretrain_run.py:164`) — чекпойнт живёт `keep_last × checkpoint_every` шагов (сейчас 2 × 25 = 50 шагов ≈ 92 мин при ~110 с/шаг). Лагуна потеряла 2 ч 14 мин пробы: ретенция удалила предмет под читающей пробой, прибор упал на финальном sha (LAG-ADR-058).

**Правило: чекпойнт живого (обучающегося) прогона напрямую не читается. До старта любой пробы/калибровки длиннее окна жизни:**

1. **Бронь** — приватная копия в каталог замера (`cp` в `<замер>/ckpt/`; при той же ФС — hardlink), либо probe-файл с широкой ретенцией как минимум краткосрочная мера — бронь всё равно обязательна для проб длиннее 2 ч.
2. **sha256 снимается с копии**, не с живого файла; расписка `RECEIPT.json` в каталоге замера: путь копии, хеш, шаг/фаза, время брони.
3. **Прибор падает рано**: хеш/верификация предмета — ПЕРЕД пробами; отсутствие предмета на финальном шаге sha — дефект прибора, не среды.
4. **Отчёт называет состояние «замороженным на момент брони»** (дата/хеш), не «текущим».
5. Калибровочные чекпойнты именовать вне glob ретенции раннера (`sft_probe_<step>.pt`-стиль), но и это не заменяет бронь для длинных проб.
6. Окно замера сверяется со скоростью трейнера: время пробы vs время жизни предмета (шагов до вытеснения × с/шаг); проба длиннее окна — только на брони.

Симптом-ключ для памяти: «чекпоинт исчез под пробой / FileNotFoundError на sha после длинной пробы».

## 5. Синк кода ПК ↔ стенд

- Fetch с GitHub **на стенде** рвётся — только git-bundle: `git bundle create axiom.bundle main` на ПК, перенос, `git fetch axiom.bundle main:…` на стенде.
- Связь с апстримом любого форка — односторонняя: fetch разрешён, push в апстрим запрещён (инвариант; см. спайн-инвариант одностороннего апстрима и `pre-push` хук).

## 6. Прочие грабли

- `pkill -f <строка>` убивает свой shell — только `pkill -x` или по pid.
- **pytest tmpdir-гигиена**: полный прогон `env/tests` оставляет ~24 ГБ в `/tmp/pytest-of-roman` (workspace-копии кейса); ретенция pytest держит 3 последних прогона → до 73 ГБ. Прогонять с `--basetemp` на свежий каталог и удалять его сразу после прогона; диск ПК 468 ГБ — два параллельных прогона = почти полный диск.
- CPU-бэкенд JAX не показателен по памяти (remat игнорируется) — выводы «влезет/не влезет» только по GPU-прогону на стенде.
- Прогоны root/контейнеров живут в другом mount namespace: их файлы (чекпойнты) из-под `roman` не видны — ущерб оценивает владелец.

## 7. Окна между ногами претрейна (протокол 05.10)

Цикл «нога ~300 шагов → сервисное окно платформы → следующая нога»:

1. **Нога завершилась** (лимит шагов или стоп-файл `~/axiom-run/STOP`): верифицировать хвост — тренд по §3.1 PRETRAIN-PIPELINE (медианы окон, стоп = 3 роста подряд), чекпойнты + resume-курсор, бюджет против `evidence/budget/pretrain-pilot-gb10.json`.
2. **Политика B3-down (владелец, 05.10): платформа стоит непрерывно**, пока конвейер активен. Watcher авто-возврата остановлен (05.10 11:15, запись в `.locks/axiom-run.lock`); возврат llm-platform — вручную по запросу владельца или при паузе конвейера (`docker start llm-platform-runtime`). Перед возобновлением ног проверить отсутствие второй GPU-нагрузки (C-040).
3. **Следующая нога**: возобновление (команда текущей ноги + `--resume`; полная команда — из `/proc/<pid>/cmdline` живого процесса или журнала):

```bash
cd ~/axiom && ~/venv-axiom/bin/python tools/pretrain_run.py \
  --run-ref pretrain-pilot-gb10 --shard-root /home/roman/axiom-run/raw-v2 \
  --tokens-root /home/roman/gb10-shared/datasets/axiom-pretrain-l3/tokens-v2 \
  --model-preset l3-full --seq-len 8192 --batch-size 1 --grad-checkpointing \
  --steps 300 --checkpoint-every 25 --ckpt-every-min 30 \
  --stop-file /home/roman/axiom-run/STOP \
  --budget-file evidence/budget/pretrain-pilot-gb10.json \
  --out /home/roman/axiom-run/pilot-l3full-endurance \
  --journal /home/roman/axiom-run/pilot-l3full-endurance-journal.jsonl \
  --metrics /home/roman/axiom-run/pilot-l3full-endurance/metrics.jsonl --resume
```

Первый шаг возобновлённой ноги сверяется с курсором (шаг > 300). Окно зафиксировать в `~/gb10-shared/.locks/axiom-run.lock`; C-040 (одна нагрузка) — до запуска.
4. **Семантика шагов (проверено 05.10)**: `--steps` — шаги ЭТОЙ ноги; `--total-steps` — абсолютный горизонт расписания, обязателен при resume (`--total-steps` ≥ шаг курсора; иначе отказ «нога не накрыта расписанием» — H4-контракт). Новая нога: `--steps 300 --total-steps 600`. Расписание WSD перестраивается на новый горизонт — **lr тёплым рестартом возвращается к пику** (шаг 301: lr 0.01 после 0.0 на 300); для полного 20B-прогона на аренде — один непрерывный горизонт, не рестарты (замечание линии-2/владельцу).
5. **Запуск ноги по ssh — грабли канала**: фон с наследованным stdin держит ssh-сессию до таймаута. Шаблон: `ssh host 'setsid nohup ... > leg.log 2>&1 < /dev/null & exit'` — stdin закрыт, хвост лога смотреть ОТДЕЛЬНЫМ вызовом. Проверку «процесс жив» — по `/proc/<pid>/cmdline` или nvidia-smi, никогда `pgrep -f` с паттерном из собственной команды (self-match ловится дважды за день — RESULTS §9, §15).
6. **Окна проб** (калибровка/RL-смоук между ногами): тот же паттерн — проба → возврат; пробы выполняются при остановленной платформе (B3-down).

## 8. Лесенка моделей для прототипирования (ADR-036)

Канон — `net/model_ladder.py` (единственный носитель): **M0 `tiny`** (CPU-секунды, wire-тесты/CI/контракты) → **M1 `small`** (~0,34M; минуты, смоуки стадий, RL-роллаут смоук, отладка приборов) → **M2 `mid`** (~30–60M, десятки минут GPU: калибровочные кривые, свипы, методологические пробы) → **M3 `l3-full`** (1,01B целевая — часы-дни).

**Правило выбора:** эксперимент стартует на самой низкой ступени, где его вопрос осмыслен; подъём — только с зелёным гейтом предыдущей. Инвариант лесенки — фичевая парность (все ступени несут полный набор фич l3, отличаясь только размерностями; композиция KDA:MLA = 3:1 везде) — гарантирует переносимость выводов по механике (провод, гейты, профили), НЕ по качеству (BPB на M2 не предсказывает BPB на M3). Dense-124m — не ступень, а ортогональный A/B-инструмент (verification-leg).

Грабля-напоминание: смоук на l3-full ≈ 8 мин компиляции + 100–500 с/шаг (ночь 06/07.10) — если вопрос решается на M1, M3 запрещён правилом.

## 9. Повторные замеры, уровни и шум (ADR-038, дельты L/M)

Допуск повторного замера — не «на глаз»: он получает происхождение (факт или решение). Порядок:

- **Происхождение сырья:** `python3 -m tools.sensors.probe --raw` — сырьё на месте, `raw_ref` факта совпадает; сырьё, изменённое после факта, краснеет (`fail`), недоступное внешнее — `unverified`, не `fail`.
- **Уровень замера:** «сквозное» (`end_to_end`) открывает гейт, «компонентное» — нет; для компонентного ускорения/сжатия объявлена пара `e2e_pair`, и `python3 tools/check_claims.py --evaluate` печатает строку «прокси-расхождение», если компонент `pass`, а сквозное — нет.
- **Окно и допуск:** у предиката по ряду обязательны `window` (`stat`, `n`, `skip_warmup`), `tolerance` и `tolerance_source`; допуск рекомендуется датчиком шума S-035 по коэффициенту вариации (`k·σ`), а не константой.
- **Шум и повторяемость:** `python3 -m tools.sensors.run_exporter --id S-035` — CV ряда ток/с между окнами и рекомендованный допуск; `python3 -m tools.sensors.run_exporter --id S-037` — детектор флапания вердиктов (по истории S-036). Флапающее утверждение не открывает гейт.
- **Гейты:** `python3 tools/preflight.py <gate>` (`--list` — перечень). `pass` — только если все требования `pass`; `unverified`/`fail` — отказ; обход — `--override-preflight <причина>` (пишется фактом S-033).
