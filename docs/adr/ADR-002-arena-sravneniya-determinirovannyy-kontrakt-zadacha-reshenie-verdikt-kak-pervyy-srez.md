# ADR-002. RL-среда и верификаторы (по рецепту базы) и отдельно — сравнительный стенд против K3

> Имя файла историческое (содержало «arena»): ID ADR стабилен, ссылки не переиспользуются.

- Date: 2026-09-11
- Status: Proposed
- Маршрут: Critical (входит в пакет ADR-001)

## Context

Заявление «наша модель обыграла Kimi K3» без воспроизводимого стенда непроверяемо: любая оценка превращается во вкусовщину и не выдерживает ревью. Дополнительно: награда RL-контура (ADR-005) обязана быть детерминированной функцией, иначе обучение вырождается в оптимизацию судьи, а не задачи.

Что доступно на 11.09.2026: веса K3 открыты (2,8T/104B активных, 1M контекста) — baseline сравним локально или на аренде, внешний API не обязателен; официальные eval-результаты вендора лежат в репозитории весов (`.eval_results/{apex-agents, deep-swe, gpqa, hle}.yaml`) и не покрывают наш домен; арена нужна как гейт и как инструмент отката (ADR-001, Reversibility).

## Decision

**Терминологическая правка 2026-09-11.** Слово «арена» было моей конструкцией и смешивало две разные сущности: (а) **среда с верификаторами** — часть рецепта базы, поставляет награду для RL; (б) **сравнительный стенд против K3** — наш инструмент отчётности. Первый срез проекта — **скелет L3, воспроизводящий рецепт**, и среда с верификаторами входит в него; стенд стенд в конвейер не входит (п. 8). Контракт среды:

1. **Task spec** (JSON): `id`, `prompt`, `workspace` (исходное состояние репозитория/файлов), `verifier`, `budget_seconds`, `max_tokens`, `thinking_budget`, `attempts`.
2. **Verifier — детерминированный**: тесты, фитнес-гейт, точное/структурное совпадение. Решение о прохождении задачи принимает код, не модель.
3. **Runner — изолированный на уровне microVM**, не контейнера: контейнерные рантаймы у вендора давали kernel panics и deadlocks от действий агента (:1481), поэтому изоляция — microVM (Firecracker-класс) с инкрементальным чекпойнтом; целевое время pause/resume — не хуже 0,5 с (у базы 133 мс и 49 мс, :1484). Без сети по умолчанию, фиксированное окружение (образ + хеш), запрет доступа к приватному корпусу из задач внешнего сравнения.
4. **Прогон (run manifest)**: снапшот модели (хеш/дата), версия среды, параметры декодирования, бюджет рассуждений, число попыток, токены, стоимость, хост инференса.
5. **Сравнение**: K3 и собственные кандидаты проходят **тот же** контракт и тот же харнесс; различия в бюджете — фиксируются в манифесте и снимают заявление о превосходстве.
6. **LLM-судья** допускается только как отдельная калиброванная метрика (k-сэмплы, golden-set), никогда — как источник награды или как основание для заявления о победе. У базы модельное судейство применяется только к непроверяемым задачам и в паре с детерминированными проверками (:1110).
7. **Механики базы, обязательные в этом слое (K3 §4.2):** среда описывает харнесс как набор конфигурируемых модулей (инструменты, системные промпты, управление контекстом, скиллы, память, субагенты) и динамически собирает разные конфигурации под группы задач — это защита от переобучения под один харнесс (:964–977). Награда привязана к **финальному состоянию среды**, а не к самоотчёту агента; агент изолирован от верификатора; публичный верификатор (диагностическая обратная связь) спарен со **скрытым** (held-out сценарии); при ограниченном бюджете попыток действуют штрафные награды (:1097–1101).
8. **Разграничение (2026-09-11):** сравнительный стенд против K3 — инструмент отчётности, **не стадия рецепта**. Конвейер скелета его не обслуживает и он его не блокирует; стенд собирается, когда появляется что сравнивать. Все требования ниже, относящиеся к равенству условий с baseline, действуют только в момент сравнения.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Внешний бенчмарк как основа** (SWE-bench-подобный) | отраслевое признание, нулевая разработка стенда | не покрывает наш домен и verifier'ы; зависит от чужого харнесса и его версии; не даёт reward для RL-контура; не решает вопрос приватности. Берём как **дополнительную** проверку, не как основу |
| **LLM-судья как основной вердикт** | дёшево, работает на «размытых» задачах | невоспроизводим, эксплуатируем наградами (reward hacking), вердикт зависит от снапшота судьи. Отвергнут как основа |
| **Статус-кво: оценка вручную/по интуиции** | ноль затрат | нет предмета доказывания; сравнение с K3 невозможно; RL нечем обучать |

## Consequences

### Positive

- Появляется воспроизводимость: любой заявленный результат проверяется повторным прогоном по манифесту.
- Арена обслуживает сразу три роли: reward для RL (ADR-005), гейт A4/A5 (conformance/drift), основание для отката на пост-тренировку открытых весов (ADR-001).
- Равенство условий с K3 становится механическим, а не декларативным.

### Negative

- Арена добавляет работу до первого результата модели: spec-формат, runner, verifier'ы, манифесты — затраты, которые не видны в «победе».
- Baseline-прогоны K3 требуют ресурсов: локально 2,8T/104B на Spark не влезает, значит аренда инференса или API (стоимость, для API — вопрос приватности задач).
- Детерминированные verifier'ы надо написать под каждый домен задачи; покрытие растёт медленно.
- Риск «бенчмарк-переобучения»: узкий набор verifier'ов начинает мерить себя. Митигация — ротация holdout-набора и запрет на обучение по holdout.

## Reversibility

**Two-way.** Контракт версионируется (arena v1 → v2), старые прогоны воспроизводимы по манифесту; смена формата spec обратима ценой перепрогона. Решение не создаёт необратимых последствий и обязано быть первым именно поэтому: без него закрывается откат, описанный в ADR-001.
