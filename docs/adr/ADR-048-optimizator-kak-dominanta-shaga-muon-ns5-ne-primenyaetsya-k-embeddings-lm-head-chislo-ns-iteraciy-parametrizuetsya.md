# ADR-048. Оптимизатор как доминанта шага

- Date: 2026-10-08
- Status: Accepted

## Context

После переписывания KDA (ADR-047, ×2.63 на шаге) раскладка шага изменилась. Диагностический проход раннера (`net/train_loop.py`, `PHASE_PROFILE_FIELDS`, шаг 4, l3-full, chunked_cc) даёт:

| Фаза | Секунды |
|---|---|
| **sec_backopt — шаг оптимизатора** | **20.40** |
| sec_kda | 2.86 |
| sec_ce (головы NTP+MTP) | 0.99 |
| sec_mla | 0.44 |
| sec_moe | 0.42 |

`sec_backopt` — это **именно шаг оптимизатора** (`train_loop.py:2155: attempt("sec_backopt", lambda: step_fn(master, grads, state, lr))`), а не backward. То есть после устранения KDA-избыточности **65% шага занимает обновление параметров** — больше, чем весь forward.

**Причина видна в коде `net/optimizer.py`:** ветка выбора — чисто по размерности, без исключений по именам:

```python
if p.ndim == 2:      return _matrix_step(...)        # Muon: newtonschulz5(m), 5 итераций
if p.ndim >= 3:      return _batched_matrix_step(...) # vmap(newtonschulz5) по экспертам
return _vector_step(...)                              # AdamW для векторов
```

Следствия:
1. **embeddings и LM head (2D, 160000×1536) попадают под Muon/NS5** — хотя Muon для входных эмбеддингов и выходной головы не предназначен: ортогонализация градиента там не имеет смысла, а стоимость квадратична. NS5 для матрицы `(m, n)` строит `A = X @ Xᵀ` размера `m×m`: для `m = 160000` это **25.6 млрд элементов ≈ 51 ГиБ** (bf16) — ровно те «52.06 ГиБ», на которых падали профильные прогоны, и ~79 TFLOP на итерацию (×5 итераций на шаг).
2. `weight_clip = 1.0` применяется ко всем матрицам, включая эмбеддинги (отдельный вопрос, здесь не решается).
3. MoE-эксперты (`vmap(newtonschulz5)`) — дорогая, но осмысленная ветка (Muon для скрытых матриц); её не трогаем.

**Ограничение метода (честно):** раскладка `sec_*` получена декомпозированным диагностическим проходом, и его фазы не интерливаются как в реальном шаге — сумма не равна времени шага. Однако масштаб (20.4 с против 2.9 с у KDA) слишком велик, чтобы объясняться погрешностью метода; вывод «оптимизатор — доминанта» устойчив.

## Decision

1. **Muon/NS применяется только к скрытым матрицам.** Embeddings и LM head выводятся из Muon и обновляются **AdamW** (`_vector_step`-семейство) — как принято в Muon-рецептах. Реализация: явный список/предикат по именам листьев (а не «любой ndim==2»), с логированием классификации (сколько параметров в каждой группе).
2. **Число NS-итераций параметризуется** (`ns_steps`, дефолт 5 сохраняется) — чтобы измерять вклад отдельно и при необходимости снижать (3 итерации — известная рабочая практика).
3. **Критерии приёмки:** (а) шаг оптимизатора по времени — **существенно ниже** текущих 20.4 с (цель — не более ~1/3 шага); (б) пиковая память NS падает так, что профильные прогоны перестают падать в 52 ГиБ OOM; (в) **loss-динамика на 20–50 шагах не хуже**, чем с текущим оптимизатором (шкала сравнения — `exp(loss)`-совпадение тенденции, а не побитовое равенство: оптимизатор меняет траекторию по построению); (г) откат — одной строкой/флагом.
4. **Классификация параметров фиксируется отчётом** (группы: Muon-матрицы, per-head, batched-MoE, Adam-векторы, Adam-embed/head) — чтобы «сколько чего» было числом, а не верой.
5. Прогоны — на GB10 с XLA-лимитом (ADR-041); при OOM-профиле не поднимать лимит до предела, а сначала устранить причину.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Исключить embeddings/head из Muon + параметр NS-итераций** (принято) | Соответствует рецепту Muon; убирает квадратичную по словарю стоимость и 51 ГиБ промежуточную матрицу; обратим | Меняет траекторию обучения (проверяется критерием «не хуже»); требует классификации листьев по именам |
| B. Оставить как есть | Ноль работы | 65% шага в оптимизаторе; 55% MFU недостижимы при любом ускорении слоёв; профили падают в OOM |
| C. Снизить только NS-итерации (5→3) | Просто | Основная стоимость — на embeddings/head, где NS сам по себе не нужен; лечит симптом |
| D. Перейти целиком на AdamW | Проще кода | Теряем Muon там, где он осмыслен (скрытые матрицы) и, вероятно, качество — регресс без основания |

## Consequences

### Positive
- Устраняется крупнейший оставшийся тормоз шага (65%) и источник 51 ГиБ аллокаций.
- Появляется измеряемая классификация параметров по группам оптимизатора.
- Обратимо флагом; остальные компоненты не затрагиваются.

### Negative
- Меняется траектория обучения: сравнение с прежними прогонами только по тенденции loss, не побитово.
- Возможна регрессия качества, если Muon для embeddings/head всё же был полезен (маловероятно, но проверяется критерием «не хуже»).
- Классификация по именам листьев хрупка к переименованиям (закрывается тестом на полный набор имён модели).
- Числа `sec_*` остаются диагностической ногой, а не точной атрибуцией шага; итоговая проверка — реальный шаг.

## Reversibility

**Обратимо, цена низкая.** Поведение переключается флагом/списком исключений; откат возвращает прежнюю классификацию. Данные и каноны не затрагиваются. Необратимых миграций нет.

## Amendment 08.10.2026 — исправление атрибуции и решения по итогам реализации

**Ошибка в Context ADR-048 исправлена (найдена харнессом, подтверждена jaxpr-дампом).** Утверждение «NS5 строит `A = X@Xᵀ` размера m×m; для m=160000 это 25.6 млрд элементов ≈ 51 ГиБ» **неверно для этого кода**: `newtonschulz5` транспонирует вход, когда `shape[0] > shape[1]`, поэтому для embedding (160000×1536) промежуточные формы — **(1536,160000)** и **(1536,1536)**; формы (160000,160000) не возникает. Значит:
- **51–52 ГиБ нельзя приписать NS на embeddings/LM head.** Наблюдавшиеся 52.06 ГиБ OOM в профиле относятся к профильной ноге `jit_loss_fn`, а не к NS. Это открытый вопрос (материализация в loss/backward-ноге), а не объяснённый факт — так и фиксируется.
- Решение ADR-048 п.1 (вывести embeddings/LM head из Muon) **сохраняется**, но по другой причине: Muon непригоден для входных эмбеддингов/tied-головы как **метод**, а не из-за мнимой квадратичной стоимости.

**Настоящая причина `sec_backopt = 20.4 с` (уточнена харнессом):** шаг оптимизатора исполняется **вне jit** (`net/train_loop.py:2503` вызывает `step_fn(master, grads, state, lr)`), а `_one` проходит по дереву **дважды** (`tree_map_with_path` × 2 при 723 листьях). NS-арифметика всего шага — порядка 3.6e13 FLOP (десятки миллисекунд), то есть измеренные 20.4 с — **хостовой overhead, а не вычисления**. CPU-смоук (малый конфиг, 138 листьев): eager **532 мс/шаг** против `jax.jit` **14.9 мс/шаг = ×36**.

**Следствие для порядка работ (решение архитектора):** доминанта устраняется **jit-обёрткой шага оптимизатора и одним проходом по дереву**, а не сменой классификации. Поэтому:
1. **Сначала** дельта «jit шага + один проход» — она и есть рычаг.
2. **Затем** приёмка ADR-048 по критерию (а): время шага оптимизатора. Критерий (а) считается достигнутым по **сумме** двух эффектов (jit + вывод emb/head из Muon), но измеряется после jit-дельты — иначе сравнение «до/после» нечестное.

**Прочие решения:**
3. **ViT-эмбеддинги** (`patch_embed`/`pos_embed`) — да, относятся к «embeddings» п.1 и переводятся в AdamW-группу (консистентность с основными эмбеддингами).
4. **`weight_clip`**: распространяется на группу `adamw_embed` (значение 1.0, как было в Muon-ветке). Прежнее поведение по клиппингу сохраняется — менять два свойства сразу нельзя.
5. **Чекпойнты состояния**: несовместимость структуры (Muon-momentum → пара (m,v)) — принимается; продолжение старых прогонов **только** с `--legacy-muon-all-2d`. Миграция состояния не делается (отдельное решение, если появится потребность продолжать именно старые прогоны).
6. **Критерий (в) «loss не хуже»**: сравнение на **50 шагах** l3-full (два режима, один сид) достаточно для сигнала; при расхождении в пределах шума — расширять до 100 шагов, но не выдавать 20 шагов за доказательство.
7. **ADR-046 (SKIP-механизм) — отдельная дельта, признаётся необходимой**: сейчас гейт красный у любой дельты, что засоряет диагностику. Реализация (свойство `requires:` + SKIP-семантика в страже/гейте) — в очереди после jit-дельты; приёмку ADR-048 не блокирует.
8. **Отчёт групп** (`evidence/kda-rewrite/optimizer-param-groups.{json,md}` + legacy-вариант) — принят в предложенном виде; требование ADR-048 п.4 выполнено: `unclassified = 0`, emb/head маршрутизированы в AdamW, скрытые матрицы остались в Muon.

**Итог по классификации (l3-full, 1.01 млрд параметров, 723 листа; после Amendment п.3 — ViT-эмбеддинги перенесены):** muon_matrix **320** листов / **279.75M**; muon_per_head 75 / 158.1M; muon_batched 138 / 325.6M; adamw_vector 187 / 0.14M; adamw_embed **3** / **246.08M** (`embedding` + tied LM head, `patch_embed` 588×384, `pos_embed` 256×384); unclassified 0.
