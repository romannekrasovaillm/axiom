# ADR-049. Spine Bank как внешний контур управления и контроля дрейфа

- Date: 2026-10-09
- Status: Proposed
- Маршрут значимости: Standard (2 триггера: new_component — второй контрольный барьер; significant_nfr — измеримое доверие контура)

## Context

Кейс Axiom ведёт собственный контур контроля на `arch-ml 0.5.3`: 53 правила `CONSTRAINTS.yaml` (C-001…C-053), спайн из 13 инвариантов (AD-1…AD-13), типизированная модель (75 сущностей), поведенческий слой (AD-036/037/038/039: `model/sensors.yaml`, `claims.yaml`, `properties.yaml`, `rule-lineage.yaml`, `opening-gates.yaml`). Этот контур проверен и здоров: `trace check` PASS (7/7 звеньев, 100%), `spine_lint` — 0 находок, `model validate model` — PASS (75 сущностей, 0 находок), `arch_drift` — 0 рёбер вне модели.

Одновременно на машине развёрнут **Spine Bank — arch-be 0.3.16** (banking edition, `/home/roman/spine-bank`), чей арсенал шире ML-редакции:

| Что даёт Bank | Чего нет в arch-ml 0.5.3 |
|---|---|
| `gate` — единый гейт (fitness + delta_guard + rule_weakened + spine_lint + trace + model_drift + arch_drift + secrets + nfr; на Standard/Critical — evidence, decision_quality, semantic_quality) | единого гейта нет: составляющие гоняются по отдельности |
| `model drift` — дрейф «модель ↔ код» (`declared-edge-unused`, `code-root-missing`, `int-contract-missing`) | нет |
| `fleet audit` — дрейф копий спайна по worktree (SSOT-проверка) | нет |
| `rules teeth` / `rules template` — измерение зубьев правил и шаблоны исполняемых проверок | нет |
| `control fp` / `digest` / `trust` — регистр ложных срабатываний, outcome-дайджест, метрика доверия 1–5 | нет |
| `redteam` / `selftest` / `review` / `delta` — мутационный тест стражей, самотест вердикта, составное ревью, дельта-цикл | частично (`delta_guard` есть, цикла propose/apply/archive нет) |

**Первый прогон Bank по Axiom (2026-10-09, read-only) нашёл следующее:**

1. **Единый гейт `arch-be gate --route standard`** — вердикт **INCOMPLETE (exit 3)**: `fitness` — SKIP по ресурсам (stand-bound правила C-040/C-042 требуют GB10, ADR-046), остальные PASS. Находки: `model_drift` — **5 warn `declared-edge-unused`** (CMP-003→CMP-002, CMP-003→CMP-005, CMP-004→CMP-002, CMP-006→CMP-004, CMP-006→CMP-005: объявлено в модели, код не подтверждает); `secrets` — **1211 warn** (шаблон `hex-token` ловит git-sha в `evidence/facts/S-036.jsonl` — ложное срабатывание).
2. **`trust` = 2 из 5.** Следующая ступень «Правила сопровождаются» заблокирована: **у 40 из 53 правил нет владельца**, зубья не измерены, у инвариантов AD-1, AD-3, AD-5, AD-6, AD-13 нет правила с подтверждёнными зубьями.
3. **`rules-report`**: у 53 правил `expiry` не заполнен нигде, `effort_hours` пуст, `exclude_glob` — 0.
4. **`rules-suggest`**: 5 кандидатов, из них 10 спецификаций без EARS-формы критериев приёмки и 4 инварианта, проверяемых только наличием текста (AD-1, AD-3, …) — «правило-упоминание» вместо проверки поведения.
5. **`fleet audit`**: 28 worktree, 14298 файлов, **51 файл с дрейфом**; `CONSTRAINTS.yaml` — **17 версий у 28 владельцев** (23 отступника), `ARCHITECTURE-SPINE.md` — 5 версий, `model/sensors.yaml` — 16, `model/claims.yaml` — 13. Это прямое нарушение SSOT спайна: одна копия должна быть каноном, остальные — производными.

Общий диагноз: предметная архитектура Axiom здорова (трассировка и линт чисты), но **управление контуром и дрейф** (жизненный цикл правил, SSOT-копии, обратные связи «модель ↔ код», доверие к вердикту) — не в полной силе.

## Decision

1. **Spine Bank (`arch-be 0.3.16`) принимается как внешний, независимый от продуктового `arch-ml 0.5.3`, контрольный барьер кейса Axiom.** Разделение ролей: `arch-ml` — продуктовая работа (спеки, ADR, handoff, обучение); `arch-be` — контроль и управление контуром (гейт, дрейф, гигиена реестра, доверие). Версии обоих бинарей пинуются здесь; смена версии — повторный прогон метрики `trust` и фиксация дельты.
2. **В `arch-harness.toml` кейса включается `[gate.required]`** с составом: `fitness`, `delta_guard`, `rule_weakened`, `spine_lint`, `trace_check`, `model_validate`, `model_drift`, `arch_drift`, `secrets`. `nfr` — на запросе; `decision_quality`, `semantic_quality`, `evidence_verify` — по мере появления входов (отчёты рубрик, EVIDENCE.yaml). Состав обязательных составляющих — часть решения, а не настройка по умолчанию.
3. **Дрейф закрывается волнами по метрике `trust` (цель — ступень 3 → 4), приоритет по цене отказа:**
   - **W1 — гигиена реестра (ступень 3):** карточки правил по фильтру Spine Bank — `owner` (все 53), `expiry` (обязателен хотя бы триггерный), `effort_hours`; инварианты AD-1/AD-3/AD-5/AD-6/AD-13 получают исполняемые правила из шаблонов Bank (`rules template apply`) или объявляются `unverifiable` с причиной — третьего состояния нет.
   - **W2 — модель ↔ код:** 5 `declared-edge-unused` — либо ребро подтверждается фактическим использованием (импорт/вызов), либо `depends_on` пересматривается решением архитектора; журнал решений по рёбрам ведёт `arch-diff` (K5).
   - **W3 — шум и FP:** 1211 `secret_literal` в `evidence/facts/*.jsonl` — в регистр FP (`control fp mark`), правило сужается по области (`changed` → исключить машинные факты) вместо глушения.
   - **W4 — SSOT флота:** канон спайна/реестра определяется по majority (`fleet audit`), расхождения сводятся; прогонные worktree старше 7 дней архивируются; `fleet audit --fail-on-dupes` становится гейтом перед кампаниями флота.
   - **W5 — машина первоисточников:** протокол Bank `reg-map` (первоисточник → цитата → маппинг → механизация → статус В/ТП/МП, снапшот + `SHA256SUMS`) применяется к внешним основаниям Axiom (техотчёт K3, лидерборды, бенчмарки) — там, где сейчас `claims.yaml` анкорит только собственные ADR.
4. **Неретроактивность (антипаттерн 6 Spine Bank):** новые карточки и правила вводятся датой; сначала режим аудита, принуждение — после зелёного прогона. Уже принятые ADR не краснеют задним числом.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Bank как второй контур + `[gate.required]`, дрейф волнами** (принято) | Полный арсенал контроля без правок кода кейса; измеримая метрика доверия; SSOT и дрейф ловятся механически; обратимо настройкой | Два бинаря и две редакции — дрейф версий; часть находок требует ручного решения архитектора |
| B. Остаться на `arch-ml 0.5.3` (статус-кво) | Один инструмент, ноль новых зависимостей | Нет единого гейта, дрейфа «модель ↔ код», SSOT-аудита, зубьев правил и метрики доверия; дрейф остаётся незамеченным (5 рёбер и 51 файл уже найдены) |
| C. Перенести арсенал Bank в ML-редакцию (патч `arch-ml`) | Один бинарь, один язык команд | Дорого, требует Rust-правок и расходится с каноном редакций; перенос в продукте идёт в обратную сторону (ML → BE) |
| D. Ручные ритуалы ревью без инструментов | Ничего не настраивать | Не машиночитаемо, доверие не измеряется, дрейф флота не виден — повтор инцидента параллельных сессий (RESULTS-2026-10-05 §2) |

## Consequences

### Positive
- Появляется измеримая шкала доверия к контуру (`trust`) и адресный список дефектов управления вместо ощущения «гейты зелёные».
- Дрейф «модель ↔ код» и SSOT-расхождения worktree ловятся до мержа и до запуска кампаний, а не постфактум.
- Реестр правил становится управляемым активом: владелец, срок, зубья, стоимость сопровождения.
- Продуктовый контур (`arch-ml`) не меняется — риск для прогонов обучения нулевой.

### Negative
- **Два бинаря и две редакции:** `arch-be 0.3.16` (banking) и `arch-ml 0.5.3` (ML) развиваются порознь; расхождение команд/семантики — реальный риск. Митигация: версии пинуются в этом ADR, смена версии — с прогоном `trust` и дельтой.
- **Второй источник правды о правилах:** единый гейт читает тот же `CONSTRAINTS.yaml`, но добавляет составляющие (`model_drift`, `secrets`, `arch_drift`), которых нет в `arch-ml`; расхождение вердиктов нужно объяснять, а не игнорировать. Митигация: `arch-be` — только контроль, продуктовый вердикт остаётся за `arch-ml`.
- **Рост тревожности:** 1211 warn по секретам и 5 warn по рёбрам могут приучить игнорировать вывод гейта. Митигация: W3 (FP-регистр и сужение области) первым делом после W1.
- `rules teeth`/`redteam` гоняются на копиях кейса — время и диск; запускать не на каждом коммите, а на релизных точках кампании.

## Reversibility

**reversible.** Решение целиком живёт в данных кейса (`arch-harness.toml`, `CONSTRAINTS.yaml`, регистр FP, отчёт): снятие `[gate.required]` возвращает прежнее поведение одним изм­енением, второй бинарь не участвует в обучении и релизах, метрики ничего не блокируют (`trust` — читающая). Откат правок реестра — `git revert` соответствующих дельт.
