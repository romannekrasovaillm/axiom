# ADR-054. Исполнение шага (donate) и фьюзинг

- Date: 2026-10-11
- Status: Proposed
- Маршрут: Standard (significant_nfr; financial_impact — ток/с определяет календарь 20B-прогона)

## Context

Все флаговые рычаги исчерпаны измерением (ADR-053 Am.3): лидер `c64_B2` = 478.7 ток/с (1.469% MFU),
S1 (3%) не взят, разрыв ×2.04; до 55% (17 917 ток/с) ×37. Профиль лидера (nsys, стационар):

- GPU-ядра **1.55 с из 34 с шага (4.6%)**; ~92k запусков ядер/шаг; ~28k DtoD-копий/шаг (**31.5 ГиБ**);
  ~420k runtime-API-вызовов/шаг — хост-поток насыщен (165 с API на 157 с окна);
- причина копий в коде: `grad_fn = jax.jit(jax.value_and_grad(loss_fn))` без donate
  (`net/train_loop.py:2873`), `step_fn = jax.jit(step)` без donate (`net/optimizer.py:366`) —
  каждый вызов таскает деревья params/grads/state через копии буферов; премисса donate уже есть:
  `params = working_params(master)` пересоздаётся каждый шаг (`net/train_loop.py:2999`);
- ядра без диспетчеризации дали бы ~10 570 ток/с ≈ 32% MFU — рамка Am.2 (≈16k ≈ 50%) достижима
  при устранении исполнения-барьера; 55% требует и укрупнения форм (B≥4, заблокирован HLO-полом
  109.38 GiB — отдельная диагностика).

## Decision

1. **Стадия-1 (эта дельта, код через handoff): donate-аргументы.**
   - `grad_fn_donated = jax.jit(jax.value_and_grad(loss_fn), donate_argnums=(0,))` — используется
     в ветке одного микробатча (`len(group) == 1`, основной путь кампании); в accum-ветке params
     нужен на каждом микровызове — там остаётся недонированный `grad_fn`;
   - `optimizer.make_step(..., donate: bool = False)`: `donate=True` → `jax.jit(step, donate_argnums=(0, 1, 2))`
     (master, grads, state потребляются); **дефолт False** — безопасен для всех существующих вызывающих,
     читающих входные деревья после шага (профайлер, SFT/RL-смоуки, тесты); тренировочный цикл передаёт
     `donate=not train_config.phase_profile` явно. При `phase_profile` — donate=False (profiler
     читает `grads` после `step_fn`);
   - grad-donate включается только в bf16-режиме (`use_bf16`): в fp32 `working_params` возвращает
     сам мастер (`params is master`), и тот же буфер читает `step_fn(master, ...)` — там donate
     запрещён, ветка оставляет недонированный вызов (edge-case найден исполнителем, закреплён тестом);
   - арифметика не меняется: donate — контракт владения буферами, не математика; паритет —
     существующие тесты + новый тест «шаг до/после donate: loss и params allclose» на CPU.
2. **Стадия-2 (после ремера стадии-1, отдельной дельтой): фьюзинг узлов графа** — Pallas-кернел
   KDA-чанка (один запуск на слой-проход вместо микро-узлов; скилл `pallas-gb10-kernel`), батчинг
   NS5-итераций; приоритет по остаточному профилю.
3. **Диагностика параллельно (архитектор, не код):** HLO-дамп B=4 — какой оп требует 88.91 ГиБ
   (пол 109.38 GiB не срезается рематом, Am.3); закрывает/переоткрывает лестницу батча B=4/8 для G3.
4. **Гейты (та же лестница ADR-050):** G1 ≥ 3% (977 ток/с) при `ядер/шаг ≤ 2000, синхронизаций ≤ 5000`;
   далее G2 ≥ 10%, G3 ≥ 20% (нужен B ≥ 4), G4 55%. Приёмка стадии-1: A/B на c64_B2 —
   DtoD/шаг < 2k (с ~28k), ток/с растёт (ожидание консервативное: шаг 34 → ≤ 25 с); loss-паритет.
5. **Честность цели:** 55% не пинится как порог (ADR-045/050 п.3); «строгий выход на 55» =
   движение по гейтам с числом на каждом, фиксация потолка измерением, если он ниже.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Donate + затем фьюзинг по профилю** (принято) | Дешёво, адрес доказан (31.5 ГиБ DtoD = размер деревьев), арифметика не меняется | Не гарантирует S1 сам по себе; требует аккуратности с accum-веткой и profiler |
| B. Сразу Pallas-фьюзинг KDA | Убирает микро-ядра в корне | Дорого, рискованно, а donate может снять большую часть барьера — профиль после стадии-1 переназначит приоритет |
| C. Смена знаменателя (FP8/MXFP4) | Кратный множитель | Отдельное решение (ADR-050 п.5е), ломает сопоставимость; барьер исполнения не убирает |
| D. Аренда внешнего GPU | Обход потолка GB10 | Не решает задачу владельца (свой бокс); ADR-050 требует сначала свой потолок |

## Consequences

### Positive
- Прямой адрес измеренного барьера (DtoD = 43% API-времени); ожидание — кратное снижение
  диспетчерской нагрузки и рост ток/с без изменения математики;
- обратимость тотальная (флаг `donate`, дефолт безопасен), паритет — существующие тесты.

### Negative
- Donate с багом = « donated buffer reused» — ловится тестами на повторных шагах;
- если DtoD-копии порождаются не jit-вызовами, а самим графом (например, prelayout-копиями),
  стадия-1 даст меньше ожидаемого — тогда профиль стадии-1 переназначит стадию-2;
- 55% остаётся за пределами гарантии: LPDDR5x-баланс и зрелость XLA на sm_121 — риск зафиксировать
  потолок ниже цели (тогда развилка FP8/аренда — отдельный ADR, ADR-050 п.4).

## Reversibility

**reversible.** Флаг `donate` (default True, откат — False одной строкой); код изолирован в
worktree `arch/mfu55-step-exec`; веса/данные не затрагиваются.

## Amendment 2 (2026-10-11, день): A/B стадии-1 и исправление диагноза — барьер есть submission-контеншн одного хост-потока

**Руки A/B** (`evidence/mfu-55/donate-ab/`, база = b2_flash 490.2 ток/с / 1.505%):

| Рука | ток/с | MFU | Вердикт |
|---|---|---|---|
| **b2f_don (B2+flash+donate)** | **491.1** | **1.507%** | **лидер кампании**; donate по ток/с нейтрален |
| c128_f_don (чанк 128) | 483.2 | 1.483% | чанк 64 оптимален и с flash (−1.6%) |
| b2f_casync (XLA_PYTHON_CLIENT_ALLOCATOR=cuda_async) | 450.7 | 1.384% | **−8%** — аллокатор не рычаг; BFC (default) остаётся (TF_GPU_ALLOCATOR инертен: в предупреждениях GPU_0_bfc) |
| b2f_topkexact (attn_topk_exact=true) | 490.7 | 1.506% | нейтрален: тайловый путь завершается jax.lax.top_k на финальном слиянии — источник столлов не убран |
| b2f_don_pre (preallocate=true) | — | — | SIGKILL: компиляция при прeаллоке 0.96 |

**Исправление диагноза (важно).** Исходная атрибуция «~28k DtoD/шаг = деревья через копии из-за отсутствия donate» **опровергнута**: после donate DtoD остались (36k/шаг) — это внутриграфовые layout-конверсии XLA. Donate оставлен в линии как гигиена буферов (нейтрален, безопасен, закрыт тестами).

**Фактическая структура шага 33.5 с (профиль b2f_don, окно 151.4 с ≈ 5 шагов):**
- GPU занят **5.0%**; **353 гэпа >10 мс = 107.7 с (71% окна)** — шаг состоит из редких гигантских простоев, а не равномерной цены запуска;
- медианы лаунчей **2.7–4.8 мкс** (не 140); хвосты p99 0.5–1.3 мс, max 354–574 мс;
- `cudaMemcpyAsync` 64 КиБ (~205 шт/окно, ~41/шаг): **p50 52 мс, max 10.4 с, сумма 69.8 с**; NVTX-атрибуция: внутри `top_k` custom-call туков и их checkpoint-remat-переисчислений (~60 top_k-туков/шаг = MLA-выборка × слои × fwd/bwd);
- **изолированная pageable-копия 64 КиБ = 0.147 мс** → блокировка контекстная: хост-поток, прогоняющий ~115k операций через драйвер, периодически встаёт целиком (submission-контеншн), а не «дорогая копия»;
- гэпы >10 мс без memcpy: 47.8 с — те же хвосты лаунчей.

## Amendment 3 (2026-10-11): стадия-2a принята и перемерена — MoE-столлы сняты, барьер сведён к submission-стоимости ~100k запусков (~30 с/шаг)

**Дельта стадии-2a** (theseus `c2b178e`, принята `78250cc`): селектор top-k роутера MoE без CUB-сорта — итеративный `argmax` с маскированием (`net/moe.py:_topk_argmax`), env `AXIOM_MOE_TOPK=argmax|jax` (default argmax, fail-closed), фолбэк на `jax.lax.top_k` вне окна k≤8/n≤64, тай-брейкинг выровнен с CUB (паритет: 22+33 теста). Паритет loss: 13.5435→12.2871 против 12.3074 (порядок суммирования).

**Перемер (`evidence/mfu-55/moe-ab/`, контроль b2f_don = jax-путь):**

| Метрика | b2f_don (jax top_k) | b3_argmax | Дельта |
|---|---|---|---|
| ток/с / MFU | 491.1 / 1.507% | **494.1 / 1.517%** | +0.6% (шум) |
| copyKind=1 (pageable H2D) | 41/шаг, **15.5 с/шаг** | **2/шаг, 0.00 с** | сняты полностью ✓ |
| гэпы GPU >10 мс | 353 шт / 107.7 с | **355 шт / 108.9 с** | не изменились |
| шаг | 33.5 с | 33.46 с | — |

**Финальный диагноз (Am.2 дополнен).** Снятие копий не сократило шаг: их блокировка была backpressure очереди запусков, а не причиной. Фактическая структура 33.5 с шага: **~29.5 с — submission ~100k запусков** (`cudaLaunchKernel` 41k = 13.25 с; `cuLaunchKernel` 39k = 10.74 с; `cuGraphLaunch` 19k = 3.27 с; `cuLaunchKernelEx` 22k = 2.24 с; avg ~0.3 мс/запуск на ARM/GB10-драйвере) + GPU 1.33 с + прочее ~2.7 с. Отсюда: **число запусков — единственный биндинг-термин**; флаги, аллокаторы, копии, donate исчерпаны измерением.

**Очередь рычагов (финальная).**
1. **Стадия-2b — Pallas-фьюзинг тела KDA-чанка** (главная дельта): ~8–14 ядер/итерацию × 6912 итераций/шаг → 1 ядро на слой-проход (54 запуска) + MoE/MLA-остаток; ожидание: ~100k → ~5–10k запусков → шаг ~5–8 с → 2–3k ток/с (6–9% MFU). Требует скилла `pallas-gb10-kernel` (sm_121: без wgmma/tcgen05, mma.sync через plgpu).
2. Проба «3→2 прохода»: B=2 без grad-checkpointing (память позволит — проверить; иначе отпадает).
3. B=4 (лестница G3): per-layer checkpoint-граница против HLO-пола 109 GiB (`hlo4-analysis.txt`).
4. 55% (G4) требует после фьюзинга ещё и тензорных ядер в тяжёлых фазах (класс (24,1,1) r89 = 25% GPU-времени) и B≥4 — длинная часть кампании, гейты ADR-050.

**Следствие для плана.** Единственный структурный рычаг — сократить число операций на хост-поток: **стадия-2 = фьюзинг** (Pallas-кернел KDA-чанка — один запуск на слой-проход вместо сотен микро-тука; батчинг NS5-итераций), плюс **стадия-2b**: per-layer checkpoint-граница для разблокировки B=4 (пол 109–121 GiB = 323 живых (B,12,8192,8192)-скоров в backward внутри while-body — `evidence/mfu-55/mla-ab/hlo4/hlo4-analysis.txt`). Тюнинг копий/аллокатора/top_k исчерпан измерением.

## Amendment 4 (2026-10-11, вечер): вехи-1/2 приняты, полный шаг — честный минус; единица фьюзинга пересмотрена (веха-3: персистентный кернел)

**Веха-2** (theseus hr-20261011-191251-05, коммит архитектора `001cfb6`, принят `533607d`): backward-кернел + `custom_vjp` для mosaic-тела; градиентный паритет 20 passed, регресс 97 passed; mosaic-тело обучаемо.

**Полный шаг A/B** (`evidence/mfu-55/kda-fused/full-step/`, chunk 32, B2, flash, donate, argmax):

| Рука | ток/с | MFU | шаг, с | loss 4 шага |
|---|---|---|---|---|
| f_jax (контроль C=32) | 457.7 | 1.405% | 35.8 | 13.5402→12.2923 |
| **f_mosaic** | **385.7** | **1.184%** | **42.5** | 13.5365→12.2936 (паритет ✓) |
| база C=64 (b2f_don) | 491.1 | 1.507% | 33.5 | — |

**Профиль f_mosaic (решающий):** **704 259 ядер/шаг** (у jax-C64 — ~100k), GPU 3.44 с (было 1.33), **cuMemcpyDtoDAsync 117k/шаг = 13.7 с**. Причина: custom-call-граница XLA (вход/выход custom_vjp на каждой из 256 итераций скана × 18 слоёв × 3 прохода) генерирует ~50 мелких операций и копий на итерацию — кернел один, сантехника вокруг него пятьдесят. Изоляция слоя (Am.3-валидация ×6.9) была честной, но единица фьюзинга слишком мала: XLA-граница дороже сэкономленных запусков.

**Следствие.** Дефолт остаётся `AXIOM_KDA_CC_IMPL=jax` (флаг mosaic сохранён как актив). **Веха-3 — персистентный кернел скана**: один запуск на слой-проход (grid=(H,), программа проходит все 256 чанков внутри, состояние S живёт в SMEM/регистрах; границы custom-call — 54 на шаг вместо 704k запусков). Если и это не снимет submission-барьер — Pallas-путь на этом шаге признаётся тупиковым (зафиксировать потолок), рычаг смещается на B=4 + NS5-батчинг.
