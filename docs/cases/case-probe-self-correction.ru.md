# Кейс: самокоррекция пробы — как механизмы Спайна опровергли диагноз архитектора

**Проект:** Axiom (LLM с нуля на JAX, GB10) · **Дата:** 07.10.2026 · **Класс:** самокоррекция инструментария / гигиена диагностики

## 1. Ситуация

Два фоновых прогона кодового харнесса (claude-code-acp) в проекте Axiom были прерваны по таймауту. В stderr обоих присутствовала строка:

```
[claude-code:unrecognized_model] {"model":"deepseek-flash","query_source":"sdk"}
```

## 2. Ложный диагноз v1 (архитектор, без пробы)

Я интерпретировал предупреждение как отказ провайдера: «имя модели мёртвое — провайдер его больше не принимает». Цепочка рассуждения: предупреждение появилось недавно → имя работало раньше (usage-логи от 24.09) → значит, провайдер его убрал. По этому диагнозу я (по выбору владельца) внёс правки в два конфига:

- `~/.config/arch-ml/config.toml`: `default_model = "glm-5.3-flash"` (с комментарием и бэкапом);
- `~/.claude/settings.json`: заменил `deepseek-flash` в пяти слотах (MODEL/HAIKU/SONNET/AUTO_MODE/SUBAGENT).

Диагноз был **неверным** — и правки сделали бы харнессы полностью неработоспособными.

## 3. Опровергающая проба

Контрольный запуск харнесса на минимальном репозитории дал за 4,6 секунды жёсткий отказ с **точным текстом**:

```
API Error: 400 The supported API model names are deepseek-flash, deepseek-v4-pro,
but you passed glm-5.3-flash.
```

Это перевернуло картину:

1. Локальный прокси (:8765) поддерживает ровно два имени — `deepseek-flash` и `deepseek-v4-pro`. Имя **живо**.
2. `[claude-code:unrecognized_model]` — **безвредное клиентское предупреждение** CLI (имя не из каталога Anthropic); оно присутствует и в полностью успешных прогонах.
3. Истинные причины сожжённых окон — устаревший TASK.md пакета в `.arch-handoff/` (агент на пробе в axiom читал чужую задачу и тратил окно на её гейты) и честно длинные задачи при тесных таймаутах. Не модель.

## 4. Самокоррекция

Обе правки откатаны из заранее сделанных бэкапов (`*.bak-20261007-*`). Контрольный проб на чистом минимальном репо: **8,0 секунд, exit 0, контракт complete** — с тем же безвредным предупреждением в stderr. Запись в хронике проекта (RESULTS §35) скорректирована датированным дополнением §35.1 — исходный ошибочный тезис не удалён, а опровергнут в том же документе.

## 5. Разбор: какие механизмы Спайна сработали

| # | Механизм | Как сработал в кейсе |
|---|---|---|
| 1 | **Проба как первоисточник (evidence-first)** | Диагноз v1 был умозрительным. Проба дала прямой артефакт — текст 400-ответа с перечнем поддерживаемых имён. Одна строка перевесила всю цепочку умозаключений. Дисциплина «факт, не память» сработала на втором витке: среда сама назвала истину. |
| 2 | **Fail-closed среда** | Прокси отклонил незнакомое имя громко и немедленно (400 за 4,6 с, с объяснением), а не стал бы молча маршрутизировать «как-нибудь». Громкий отказ — это то, что делает опровержение дешёвым и недвусмысленным. |
| 3 | **Обратимость правок (backup-before-edit)** | Обе правки сделаны с датированными бэкапами по конвенции каталога конфигов. Откат занял две команды и ноль размышлений. Обратимость — не секция в ADR, а привычка, которая превращает ошибку в незаметное происшествие. |
| 4 | **Изоляция предмета замера** | Первый проб на axiom утонул: агент прочитал устаревший TASK.md пакета и потратил окно на чужие гейты. Проб на чистом минимальном репо (git init + README) уложился в 8 секунд. Это тот же урок, что «бронь предмета замера» (ADR-058 Лагуны): чистота предмета — условие валидности замера. |
| 5 | **Честные журналы (append-only хроника)** | Ошибочный тезис §35 не вычищен, а опровергнут датированным §35.1 в том же документе. Хроника — не витрина успеха, а протокол мышления; коррекция без стирания сохраняет след ошибки, на котором учатся. |
| 6 | **Структурированный контракт исполнителя** | JSON-контракт харнесса (status/assumptions/open_questions) вскрыл расхождение «stdout печатает complete — result.json на диске stale»: видно, что агент не дошёл до финализации. Контракт сделал состояние наблюдаемым. |
| 7 | **Guard-рельсы, формирующие поведение** | R4-страж заблокировал `rm -rf` тестового каталога → проба поехала в свежий каталог без удаления — что и требовалось для изоляции (п. 4). Рельса не просто остановила, а выталкивает в лучший дизайн эксперимента. |
| 8 | **Единственный носитель — и цена его нарушения** | Имя модели жило в трёх местах (реестр прокси, 5 слотов settings.json, config.toml) без объявления иерархии. Рассинхрон носителей и породил ложный след. Правило «у значения один носитель» применимо не только к числам KPI, но и к именам/конфигурациям внешних систем. |

## 6. Чего Спайн не спас (честно)

Сам ложный диагноз произошёл **несмотря на** действующую дисциплину evidence-first: я выдал вердикт о «мёртвом имени» без единого пробы, а ошибочный ops-тезис попал в хронику проекта до всякой верификации. Механизмы Спайна поймали ошибку только на **следующем** витке — когда владелец прямо попросил проверить имя. Вывод: вердикт о внешней системе без пробы — та же экономия, что «спека после кода»; цена ошибки была низкой только потому, что правки оказались обратимыми (п. 3), а не потому, что их не следовало делать.

## 7. Проверяемые следствия

1. Верификационные пробы харнесса — только на чистом минимальном репо без пакета (правило записано в RESULTS §35.1 и этот кейс).
2. Классификация предупреждений: `unrecognized_model` = косметика клиента; маскировать или «чинить» не нужно.
3. Бэкапы конфигов перед правкой — обязательны (сработали дважды за кейс).
4. Имя модели внешней системы: носитель — реестр прокси; слоты CLI и конфиги харнессов — потребители. Следующая правка имени делается в реестре прокси, а не в потребителях.
