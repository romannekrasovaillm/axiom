## 1. Роли и границы

Одна механика обслуживает трёх потребителей: **reward RL-контура** (ADR-005), **conformance-гейт A4**, **drift-проверка A5**. Сравнительный стенд против K3 — не часть среды (ADR-002 п.8) и не блокирует скелет, но использует те же верификаторы и контракт манифеста, когда появляется что сравнивать.

Среда НЕ содержит: обучения (вне её), генерации траекторий чужих моделей (отдельный харнесс, CMP-006), судейских моделей (запрещены в контуре награды, AD-2).


Инвариант: `budget_seconds`, `max_tokens`, `thinking_budget`, `attempts` одинаковы для всех кандидатов на этой задаче (AD-3). Расхождение фиксируется в манифесте и снимает право на заявление о превосходстве.

## 3. Workspace и деградация

Workspace — git-bundle снапшот кейса (репозиторий с ARCHITECTURE-SPINE.md, CONSTRAINTS.yaml, docs/adr, model/). Агент работает headless, финальное состояние — коммит в рабочей ветке. Вердикт выносится только по финальному состоянию среды, не по самоотчёту агента (ADR-002 п.7).

**Деградация** — появление нарушений, отсутствовавших в `base_commit`. Сигнатура нарушения — пара `(rule, file)` из `issues` FitnessReport; строка `line` в сигнатуру не входит (нестабильна при правках).

## 4. Верификаторы (reference: arch-ml CLI)

| Верификатор | Команда | Интерфейс | Что проверяет |
|---|---|---|---|
| fitness | `arch-ml control check <ws> --constraints <c> --json` | exit code + JSON `FitnessReport` | 32 правила CONSTRAINTS (C-001…C-032) |
| spine | `arch-ml control spine <ws>/ARCHITECTURE-SPINE.md` | exit code + текст | дубли AD, пустые Binds/Prevents/Rule, заглушки, непиннутые версии, битые ссылки AD |
| trace | `arch-ml trace check <ws>` | exit code + отчёт | REQ → NFR → AD/ADR → CMP → правило |
| tests | `objective.tests_cmd` в workspace | exit code | задачный объектив (тесты реализации) |

Контракт `FitnessReport` (SDK v1, поле `--json`): `passed: bool`, `issues: [{file, line, rule, message, severity: error|warn}]`, `summary: string`, `durations`, `inherited`. Вердикт учитывает только `severity: error`; `warn` пишется в манифест без влияния на награду.

Верзия верификатора пиннится: `arch_ml_build` (хеш сборки CLI) + `constraints_sha256` + `hidden_constraints_sha256` — в каждый манифест (AD-4).

## 5. Вердикт и награда — детерминированные функции финального состояния

`gates(ws) = fitness ∧ spine ∧ trace ∧ tests` (все — из §4).

**restore-gates** (исходно испорченный кейс): `pass ⇔ gates(final)`.
**keep-gates-implement** (живая задача на чистом кейсе): `pass ⇔ gates(final) ∧ tests(final)`.

**Награда за попытку** (все компоненты — детерминированные функции артефактов прогона):

```
r = 1.0·[pass]
  + 0.5·soft
  − 0.25·min(new_violations, 4)/4
  − 1.0·[spent_tokens > τ·b₀]                    (бюджетный контроль усилия, K3 :879)

soft (restore)         = доля устранённых базовых нарушений: 1 − |viol(final)∩viol(base)| / |viol(base)|
soft (keep-implement)  = доля пройденных задачных тестов
new_violations         = |viol(final) \ viol(base)|, сигнатуры (rule, file)
τ = 2 (v1), b₀ = max_tokens задачи
```

**Урок H2.1 (обязателен к исполнению):** разреженный бинарный reward вырожден на малых моделях — advantage≈0, градиент нулевой (измерено на Qwen2.5-0.5B, `grpo_manual.py`, стенда vast.ai 4090). Плотная компонента `soft` — не опция, а требование; при этом она остаётся механической (доли гейтов/тестов), не модельной — AD-2 не нарушается.

Агрегация по попыткам в v1: награда эпизода = награда последней попытки; число попыток ограничено `attempts` и фиксируется в манифесте. Изменение агрегации — только через пересмотр спеки (версия environment).

### 5.1. Дисциплина сэмплирования (дисперсия для RL)

Верификатор детерминирован, поэтому **единственный источник дисперсии reward внутри GRPO-группы — декодирование**. При greedy (temperature=0) все rollout'ы одной задачи совпадают → advantage≈0, градиент нулевой — та же вырожденность, что в уроке H2.1, из другого источника.

- **RL-rollout'ы**: temperature > 0 (v1: 0.7), seed на каждый rollout, G = 8 rollout'ов на задачу (размер группы GRPO).
- **Вердиктные прогоны A4/A5**: temperature = 0 либо seed-воспроизводимый режим; вердикт детерминирован от финального состояния при любом декодировании, повторный rollout — best-effort по seed (недетерминизм GPU-инфраструктуры помечается в манифесте).
- Если при temperature > 0 дисперсия награды внутри группы ≈ 0 — задача вырождена (слишком лёгкая/тяжёлая): снимается с лесенки по результатам кальбровки §10, а не компенсируется модельным судьёй (AD-2).
- Все кандидаты на задаче ходят с одинаковыми декодирующими параметрами (AD-3); параметры — в манифесте.

LLM-судья не участвует в награде ни в какой роли (AD-2). Допускается как отдельная калиброванная метрика вне контура награды.

## 6. Скрытый верификатор (holdout)

Парность по рецепту базы (ADR-002 п.7): публичный CONSTRAINTS.yaml лежит в workspace и виден агенту; **holdout-набор правил** (`hidden_constraints`) хранится вне workspace и применяется только на вердикте. `H` в difficulty — доля скрытых правил от общего числа активных.

Ротация: holdout-пул обновляется между поколениями задач; **обучение по holdout запрещено** (NFR-001), правила не участвуют ни в SFT, ни в отборе награды до ротации. Утечка скрытого набора в prompt/workspace = брак задачи, задача отзывается.

## 7. Runner (изоляция)

- **microVM Firecracker-класса**, не контейнер: контейнерные рантаймы у вендора давали kernel panics и deadlocks от действий агента (ADR-002 п.3 со ссылкой K3 :1481).
- Сеть по умолчанию отключена; образ и его хеш зафиксированы в манифесте.
- Цель pause/resume — не хуже 0,5 с (у базы 133 мс / 49 мс, K3 :1484).
- **AD-7:** инференс/rollout на Spark — одна модельная нагрузка за раз; генерация задач и обучение исполняются вне Spark (обучение — на аренде, INT-001).
- Веса кандидатов — симлинки на `~/gb10-shared`, копий нет (C-032); хеш пиннинга — по содержимому (AD-4).

## 9. Лесенка сложности

Оси: `R` — число активных правил CONSTRAINTS; `H` — доля скрытых правил; `S` — объём кейса (файлы × строки спек); `B` — бюджет (`budget_seconds`, `attempts`).

**Решение архитектора (12.09.2026, конфликт реализации): ось R зафиксирована** — workspace несёт полный набор правил (R=32): trace-верификатор требует все связи AD→правило (≥10 правил), редукция R<10 ломает трассируемость. Уровни различаются не редукцией правил, а объёмом порчи (атомы повреждения), долей скрытых правил `H` и бюджетом попыток.

| Уровень | Порча (атомов повреждения) | H | B | Назначение |
|---|---|---|---|---|
| L0 | 1 | 0 | 1 попытка | механика гейтов, тривиальная порча |
| L1 | 3 | ≤0.25 | ≤2 | поиск деградации по нескольким правилам |
| L2 | 5+, комбинированная | ≤0.4 | ≤3 | комбинированная порча + живая правка |
| L3 | многофайловая | ≤0.5 | ≤3 | полный набор, многофайловая деградация |

Масштабирование кейса ради честной редукции R — отклонено: вырастает ось S и обслуживание ради косметики лесенки.

**Объём скелета L3 (v1-scope):** ≥20 публичных задач = {real, corruption} × {L0, L1} × ≥5; holdout-пул ≥50 задач. Целевой holdout n≥200 (NFR-001) — за пределами скелета, до выбора масштабного класса.

Источники: **corruption** — детерминированный мутатор чистого кейса (seed → фиксированный набор повреждений: удаление секций ADR, разрыв трассируемости, битые ссылки AD); **real** — отобранные владельцем кейсы контура; **holdout** — невыпущенные кейсы/правила.

## 10. Кальбровка — precondition запуска RL

До старта обучения: прогон K3 (baseline) на полном skeleton-наборе по контракту §2–§8. **Критерий готовности: pass-rate ∈ [10%, 90%].** Вне коридора лесенка пересобирается до обучения, не после. Фиксируется: распределение вердиктов, среднее число попыток, стоимость, дисперсия награды внутри GRPO-групп (§5.1).

**Честность сигнала (обязательные дисклеймеры):**

1. Кальбровочная **матрица модель × набор задач** публикуется целиком (включая провальные ячейки) — в `evidence/`, с пиннингом.
2. **Ось self-referential по построению**: гейты написаны в этом же контуре — это заявленное свойство домена (ADR-006), а не скрытый конфликт; все заявления о результате — только на объявленной оси с пиннутым манифестом (AD-1), паритет на общих бенчмарках не заявляется.
3. Награда механическая по построению: отсутствие модельного судьи — не дефект, а решение AD-2; отчёты о качестве маркируются «verifier-only».

Результаты кальбровки — первый артефакт в `evidence/` (пиннинг обязателен).

## 11. Критерии приёмки реализации

1. Схемы §2 и §8 валидируются на эталонных примерах (валидный/невалидный).
2. Верификатор парсит FitnessReport JSON и отличает error от warn.
3. Мутатор порчи воспроизводим: одинаковый seed → байт-в-байт одинаковый повреждённый кейс.
4. Загрузчик манифестов отклоняет прогон без любого из полей пиннинга.
5. Кальбровочный скрипт прогоняется end-to-end и пишет отчёт в evidence/.
6. Награда воспроизводима: повторный вердикт по тому же финальному состоянию даёт тот же r до знака (A5-свойство, AD-2).
7. В workspace отсутствуют реальные файлы весов (C-032), runner не даёт сети (§7).
