# Mosaic-перенос KDA-решения: вердикт по применимости (10.10.2026, GB10, jax 0.11.2)

## Что достигнуто

**Ядро впервые исполнилось на GB10** (bf16): `status: ok`, 3.8 с. До этого было 5 блокирующих дефектов (имя, `grid_names`, 2D-операнды, транспозиция RHS, транспорт раскладок) — все закрыты, инфраструктура работает.

## Два препятствия, одно из которых структурное

| Препятствие | Факт | Природа |
|---|---|---|
| **fp32-операнды** | `NotImplementedError: Unsupported operand type: f32` в `plgpu.mma` | **структурное ограничение API 0.11.2**: MMA принимает bf16/fp16/fp8/int8/int4, **f32 не поддерживается**. fp32-путь решения (пин `F32_F32_F32` в Triton-версии) на Mosaic **невозможен** |
| **численная корректность bf16** | `max_abs = 1.9e10` (rel ≈ 2e9) при исполнении | **дефект реализации цепочки**, не API: в `body` шаг `(I + power)` собирается из `mma` без явного `+I` и с RHS без `.T` (это отметил и исполнитель); Neumann-цепочка (7 множителей × выгрузки в SMEM) собрана не по прототипу, который проверен (там `(L@L)@L` давал `rel ≈ 1e-2`) |

## Вердикт

1. **fp32-путь на Mosaic закрыт структурно.** Для KDA-решения, где нужна точность выше bf16 (наш Triton-путь пиннит `F32_F32_F32`), Mosaic **неприменим** — это не «доделать ядро», а ограничение платформы API.
2. **bf16-путь возможен, но ценность ограничена**: даже при корректной реализации цепочка из ~7 умножений с выгрузками в bf16 накапливает ошибку (в прототипе `rel ≈ 1e-2` на цепочке из двух умножений), а KDA — операция, где ошибка решения системы распространяется на весь слой. Triton-версия в bf16 укладывается в допуск (bad=0.00% при atol), но в fp32 точнее.
3. **Инфраструктура Mosaic — рабочий актив**: проверены и задокументированы раскладки (`MMA_LHS` без транспозиции, `MMA_RHS` при памяти `(n,k)` + `.T`, `MMA_ACC`), SMEM-переход между шагами цепочки, Lane-семантика, `grid_names`, `scratch_types=[SMEM(...)]`. Это применимо к **compute-bound частям в bf16** — прежде всего MLA/attention и MoE, где точность bf16 приемлема и где сейчас 35 712 запусков класса `grid=(12,1,1)` и 191 488 микро-ядер.

## Рекомендация

- **Прекратить Mosaic-перенос именно KDA-решения** (fp32-путь невозможен, bf16-путь уступает Triton по точности на критичной для модели операции).
- **Перевести Mosaic-усилие на bf16-пригодные compute-bound части** (MLA/MoE) — там ограничение API не мешает, а выигрыш от укрупнения ядер адресует измеренный барьер 0.11.2 (395 тыс. прямых запусков).
- Альтернатива, если KDA-ядро всё же нужно: **гибрид** — Mosaic для bf16-частей, Triton/fp32 для решения систем (то есть наш существующий `AXIOM_KDA_SOLVE=pallas` остаётся, а Mosaic идёт в MLA/MoE).
