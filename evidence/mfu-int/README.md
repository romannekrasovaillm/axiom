## Находки, требующие решения (не выводы)

1. **CE-backward (3.84 с, 20% шага) не реагирует ни на dtype, ни на `ce_chunk_tokens`.**
   Гейт точности на головах ЕСТЬ (`compute_dtype.gemm`, `net/model.py:711,759`) — значит
   причина не в dtype, а в чём-то неучтённом (softmax/gather по оси словаря 160k,
   градиент таблицы эмбеддингов ~246M параметров, пересчёт чанка под `jax.checkpoint`).
   Механизм **не измерен**: нужна более тонкая декомпозиция CE-ноги.

2. **Спарс-MoE (line-1, `ragged_dot` top-2/12): FLOPs падают, wall-time MoE — нет.**
   Сравнение с до-merge замером той же клетки (dense: moe 0.166 fwd / 0.515 bwd) даёт
   в B 0.25 / 1.05. Но это **не чистый A/B**: различаются ещё и политика remat, поэтому
   вывод «спарс дороже» пока НЕ утверждается — нужен A/B sparse vs dense при равных прочих.

3. **Ширина чанка `chunked_cc` не проверена.** Прежний вывод «kda_chunk 64→256 пуст»
   измерял `kda_wyut_chunk`, который при заданном `chunk_size` не читается
   (`net/kda.py:687-704`; `chunk_size` приходит из `--chunk-size`). Настоящий рычаг —
   `--chunk-size` ∈ {64, 128, 256}.

**Откат:** все три прогона — конфигурационные (конфиг + env), кода не меняли; журналы
`run{A,B,C}-*.jsonl` в этом каталоге воспроизводят условия.
